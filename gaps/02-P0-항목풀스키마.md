# 결정서

## ① 결정

### 구조 — 전역 카탈로그 + 템플릿은 참조만

```python
# backend/app/schemas/template.py

class Slot(BaseModel):
    """항목의 해결 조건 한 칸. 역할 3이 쓴다."""
    key:      str              # "amount"
    label:    str              # "금액"
    cues:     list[str]        # 충족됐다고 볼 예문 3개
    blockers: list[str] = []   # 취소됐다고 볼 예문 3개 (재발 판정용, W3)

class Item(BaseModel):
    """전역 항목 카탈로그의 한 줄. 템플릿을 넘어 ID가 안정적이다."""
    id:       str              # "budget_approval" — 영문 snake_case
    label:    str              # "예산 승인" — 한국어
    aliases:  list[str]        # 이 항목 얘기가 나왔다고 볼 예문 5개
    keywords: list[str] = []   # 확실한 신호만. 선택
    slots:    list[Slot]       # 1~4개

class TemplateItem(BaseModel):
    """템플릿이 카탈로그에서 고른 항목 + 이 유형에서의 성격"""
    item_id:    str
    layer:      Literal[1, 2]   # 1층 반대사유 / 2층 필수 항목
    default_on: bool
    priority:   int             # 낮을수록 위

class Template(BaseModel):
    id:    str                  # "insurance_consult"
    label: str                  # "보험 상담"
    items: list[TemplateItem]   # 30~50개
```

**목록에 없는 발화**(§2-1)는 예약 항목 `_other` 하나에 원문 그대로 쌓는다. 분류하지 않는다.

```python
class OffListMentions(BaseModel):
    item_id: Literal["_other"] = "_other"
    raw: list[tuple[float, str]]   # (시각, 원문)
```

### 1층과 2층은 상태 모델이 다르다

| | **1층 · 반대사유** | **2층 · 필수 항목** |
|---|---|---|
| 무엇의 상태 | 상대의 상태 | 내 행동의 완료 여부 |
| 상태 수 | 5개 (⚪🔴🟡🟢 + 재발) | **2개** (☐ / ☑) |
| 방향 | 오르내림 · **재발 있음** | **단조 증가** |
| 슬롯 | 사용 | **사용하지 않음** |

**2층은 슬롯을 쓰지 않는다.** 언급 여부만 판정하므로 `aliases`만 있으면 되고, `slots`는 비워둔다. 자세한 규칙은 `03`.

### 상태는 슬롯 충족으로 파생된다 (1층만)

| 슬롯 충족 | 상태 |
|---|---|
| 0개 | 🔴 나왔는데 못 끝냄 |
| 일부 | 🟡 일부 끝남 |
| 전부 | 🟢 끝남 |

**이 규칙이 🟡을 자동으로 정의한다.** 슬롯 없이 가면 "일부 끝남"을 사람이 매번 판단해야 하고 채점 기준이 안 나온다.

> ⚠️ **여기까지가 이 문서의 범위다.** *언제* 상태가 움직이는지, **재발**을 어떻게 판정하는지는 `03`이 정한다. 이 문서는 "무엇이 충족되면 해결인가"(항목별)만 정하고, `03`은 "언제 어떻게 움직이나"(공통)를 정한다.

### 저장 위치와 형식

| | 경로 | 형식 | 누가 쓰나 |
|---|---|---|---|
| 전역 항목 카탈로그 | `backend/app/templates/catalog.yaml` | YAML | 조장 (역할 5) |
| 템플릿 | `backend/app/templates/{id}.yaml` | YAML | 조장 (역할 5) |
| 수집된 실제 발화 | `backend/app/templates/harvested/{item_id}.jsonl` | JSONL | 자동 |

**YAML로 간다.** 조장이 손으로 쓰고 PR로 리뷰받는 파일이므로 JSON은 부적합하다. 로드 시 Pydantic으로 검증한다.

**`id`는 영문 snake_case, `label`은 한국어.** `id`는 fixture JSON·DB·모듈 간 계약에 쓰이는 기계용 식별자이고, `label`은 화면에 뜨는 사람용 이름이다.

### 예문 규모

| | 개수 | 40항목 기준 | 누가 | 언제 |
|---|---|---|---|---|
| `aliases` | **항목당 5개** | 200문장 | 조장 | **W1** |
| `slots[].cues` | **슬롯당 3개** (항목당 슬롯 평균 2개) | 240문장 | 조장 | **W3** |
| `slots[].blockers` | **슬롯당 3개 · 상위 12항목만** | ~72문장 | 조장 | **W3** |
| | | **합 512문장** | | |

**W1에는 `aliases` 200문장만 채운다.** 역할 2(매칭)는 이것만 있으면 착수할 수 있고, 역할 3(상태)이 `cues`를 기다린다. 계약 동결 주에 512문장을 다 쓰는 건 무리다.

**`blockers`는 전 항목에 달지 않는다.** 재발은 §2-2가 보여주듯 특정 항목(예산·결정권자·일정)에 몰린다. 상위 12항목에만 달고, W3 실측 후 필요한 항목에 추가한다.

### 예문은 손으로 쓰고 데이터로 자란다

수기 예문 5개는 임베딩 매칭에 적을 수 있다. 그래서 **fixture 라벨링이 예문을 자동으로 보강하게 한다.**

```
fixture 라벨링 (전원 부역)
   → 실제 발화에 item_id가 붙는다
   → harvested/{item_id}.jsonl 에 자동 적재
   → 매칭기는 aliases(수기 5) + harvested(실제 N) 를 함께 인덱싱
```

`aliases`는 **씨앗**이고 `harvested`는 **자란 것**이다. 템플릿 YAML은 손으로 읽을 수 있는 크기로 유지되고, 표현 사전은 라벨링을 할수록 두꺼워진다. §4-5가 "진짜 비용"이라 한 템플릿 인건비가 **평가 데이터 작업과 같은 노동으로 합쳐진다.**

### 검증 규칙 (로드 시 강제)

- `TemplateItem.item_id`는 카탈로그에 존재해야 한다
- 한 템플릿 안에서 `item_id` 중복 금지
- **2층 항목은 `default_on=true` 강제** — 반드시 다뤄야 하는 것이므로 항상 켜져 있다
- **2층 항목은 템플릿당 12개 이하** — 넘으면 항목이 너무 잘게 쪼개졌다는 신호. 법정 대분류 단위로 합친다. *(화면 ② 가운데 열이 스크롤 없이 담을 수 있는 한계)*
- `aliases` 최소 3개 (권장 5개)
- **1층 항목의 `slots`는 1~4개.** 5개를 넘으면 항목을 쪼개라는 신호 → 공백 `08`의 조기 경보
- 2층 항목은 `slots` 비어 있어야 한다
- `default_on=true`인 1층 항목은 3~7개 (§5-2의 "1차 기본 세트 5개")

### 예시 — 이 한 줄이 작성 표준이다

```yaml

  label: 예산 승인
  aliases:

    - 생각했던 것보다 좀 있네요
  keywords: [예산, 결재, 금액]
  slots:
    - key: amount
      label: 금액
      cues:
        - 월 12만원 정도면
        - 그 금액이면 괜찮습니다

      blockers:            # W3에 채움
        - 그건 좀 부담이네요
        - 다시 생각해봐야겠는데
    - key: approval_process

      cues:

        - 팀장님 결재만 받으면 됩니다

      blockers:
        - 위에서 좀
```

## ② 근거

**예문 리스트로 간 이유.** 정규식은 조장이 유지보수할 수 없고, 키워드만으로는 "위에 물어봐야"처럼 단어가 겹치지 않는 표현을 못 잡는다. 예문은 도메인을 아는 사람이 쓰기 쉽고 임베딩에 그대로 들어간다. `keywords`는 "예산"처럼 확실한 신호에만 선택적으로 달아 부스트로 쓴다.

**슬롯으로 간 이유.** §4-2가 "금액과 승인 절차가 둘 다 나와야 🟢"라고 한 걸 일반화한 것이다. 슬롯이 없으면 🟡을 정의할 방법이 없고, 정의가 없으면 **채점할 수 없다.** 역할 3의 지표가 성립하려면 정답이 있어야 한다.

**전역 카탈로그로 간 이유.** 템플릿마다 항목을 새로 정의하면 2차 미팅에서 1차 항목을 이월할 때(§5-2) ID가 맞지 않는다. **차수별 누적이 해자(§7-2)인데 그 연결이 깨진다.** 카탈로그에서 고르는 구조면 이월이 항상 성립하고, 유형을 늘려도 공통 항목은 재사용된다. 공백 `04`와 직결된다.

**예문을 5개로 줄이고 harvested로 보강하는 이유.** 항목 40개에 예문 10개씩이면 400문장이고, W1 안에 못 쓴다. 5개면 200문장이라 가능하다. 부족한 밀도는 fixture 라벨링에서 나오는 실제 발화로 메운다 — **어차피 해야 하는 작업이 표현 사전을 두껍게 만든다.**

**`blockers`가 임베딩 매칭인 이유.** 모델에게 *"이 발화가 저 예문과 닮았나"* 만 묻고 판단은 규칙이 한다. §2-3이 카드에서 *"LLM은 마지막 한 칸에서 문장만 쓴다"* 고 한 것과 같은 구조다. LLM에게 "재발했나"를 통째로 물으면 채점 기준이 사라진다.

## ③ 탈락 대안

**(1) 정규식 표현 사전** — 정확하게 통제할 수 있지만 조장이 쓰고 고칠 수 없다. 템플릿 저작이 개발자 작업이 되면 §4-5가 말한 확장 구조(사용자·기업이 직접 등록)가 막힌다.

**(2) 키워드만** — 가장 싸지만 "위에 물어봐야" "여력이…"처럼 항목명과 단어가 안 겹치는 표현을 놓친다. §2-1이 든 예시가 전부 이런 것들이라 제품이 성립하지 않는다.

**(3) 항목 ID를 템플릿 로컬로** — 템플릿 파일 하나만 보면 되어 단순하지만, 차수 간 이월이 깨지고 유형을 늘릴 때 공통 항목이 중복된다. 해자를 포기하는 선택이다.

**(4) 상태 판정 기준을 자유 텍스트로** — `"금액과 승인 절차가 둘 다 나와야 함"`을 문장으로 두고 LLM이 판정하게 하는 안. 유연하지만 **채점 기준이 사라진다.** 역할 3이 "정확도 N%"를 말할 수 없게 되고, 최종 Q&A에서 가장 아픈 질문이 여기서 나온다.

**(5) 예문 10개 이상** — 매칭 정확도는 더 높겠지만 W1 안에 못 쓴다. 5개 + harvested로 시작하고, W3에 실측 F1을 보고 부족하면 그때 늘린다.

**(6) 2층에도 슬롯 적용** — 일관성은 있지만 2층은 "언급했나"만 보면 되므로 슬롯이 낭비다. 작성량만 240문장 늘어난다.

## ④ 계약 영향

- [ ] 건드리지 않음 — 담당자가 결정합니다
- [x] **P0 계약을 건드립니다**  *(P0 항목이므로 해당)*

**이 스키마는 역할 경계와 일치한다**

| 필드 | 소유 | 지표 |
|---|---|---|
| `aliases` `keywords` | **역할 2** | 매칭 F1 |
| `slots[].cues` `slots[].blockers` | **역할 3** | 상태 정확도 · 재발 재현율 |
| `layer` `default_on` `priority` | **역할 5** | 이월 정확도 |

세 사람이 같은 파일의 다른 칸을 채운다. **스키마 하나가 분담표가 된다.**

**파급되는 것**

| 대상 | 어떻게 |
|---|---|
| **`03` 상태 전이표** | 슬롯 충족 → 🔴🟡🟢 파생은 여기서 정했다. `03`은 **전이 시점과 재발 판정**만 정한다 |
| **`04` 미팅↔딜 연결** | 전역 `item_id`가 있어야 차수 간 이월이 성립한다 |
| **`08` 항목 30~50개** | `slots` 5개 초과, 2층 12개 초과가 "쪼개라/합쳐라"는 신호. 검증 규칙이 곧 조기 경보다 |
| **fixture 스키마** | 라벨은 `item_id` + `slot_key` 단위로 붙는다. 라벨링이 곧 `harvested` 적재다 |
| **역할 5 저작 도구** | YAML을 직접 편집하거나, CRUD 화면이 YAML을 읽고 쓴다 |
