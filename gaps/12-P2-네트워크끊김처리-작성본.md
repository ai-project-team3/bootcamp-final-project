# 결정서

## ① 결정
> 한 문장으로. "무엇을 이렇게 한다"

**상태 저장은 서버를 기준으로 하며 상태 변화가 발생할 때마다 즉시 스냅샷하고, 연결이 끊기면 같은 세션 ID로 자동 재접속한 뒤 서버의 최신 스냅샷을 다시 받아 화면을 복구한다.**

## ② 근거
> 왜 그렇게 정했나. 조사했으면 출처를 남기세요

- 이 제품의 핵심 데이터는 원문 오디오 자체보다 **현재 objection 상태와 그 근거**이므로, 상태 변화 시점을 기준으로 저장하면 가장 중요한 정보 손실을 줄일 수 있다.
- 클라이언트만 상태를 가지고 있으면 브라우저 새로고침, WebSocket 종료, 네트워크 끊김 시 복구가 어렵다.
- 서버를 authoritative source로 두면 역할 1의 실시간 세션과 역할 3의 상태 추적이 같은 최신 상태를 바라볼 수 있다.
- 주기적 저장만 사용하는 것보다 **상태 변화 시 즉시 저장**하는 편이 이벤트 수가 많지 않은 현재 구조에서 단순하고, 중요한 변화 직후 끊겨도 손실 가능성이 낮다.
- MVP에서는 끊긴 동안의 모든 오디오를 완벽히 복원하는 것까지 범위를 넓히지 않고, **끊기기 전까지 확정된 상태를 보존하고 재접속 후 이어가는 것**을 우선 목표로 한다.
- 재접속 과정에서는 끊김이 있었다는 사실을 UI에 표시해, 누락 구간이 없는 것처럼 보이지 않게 한다.

## ③ 탈락 대안
> 무엇을 안 골랐고 왜. 최소 하나

1. **클라이언트 상태만 유지하는 안**
   - 탭 종료·새로고침·브라우저 오류 시 상태를 잃을 수 있다.
   - 동석자나 다른 클라이언트와 상태를 맞추기 어렵다.

2. **5초·10초 등 일정 주기 스냅샷만 하는 안**
   - 저장 직후 상태가 바뀌고 연결이 끊기면 최신 상태를 잃을 수 있다.
   - 상태 변화 이벤트가 상대적으로 적은 구조에서는 이벤트 기반 저장이 더 단순하다.

3. **끊긴 동안의 오디오까지 전부 로컬 버퍼링해 완전 복구하는 안**
   - 가장 이상적이지만 W1~W3 MVP 범위에 비해 구현 복잡도가 크게 증가한다.
   - 우선순위는 상태 보존과 재접속 성공이며, 오디오 완전 복구는 후순위로 둔다.

**판단 근거:** 네트워크 세션의 복구 전략과 상태 저장 시점을 정하는 것으로, P0의 상태 의미나 고객 연결키 자체를 변경하지 않는다.  
세션 복구용 `session_id`는 미팅↔고객 연결키와 분리해 사용한다. 만약 기존 P0 #4 연결키 구조를 재접속 키로 직접 사용하도록 변경해야 한다면 조장에게 올린다.

## ⑤ 첫 구현 스텝
> 이 결정대로면 W1(9/14~)에 내가 무엇부터 만드나

1. WebSocket 에코 서버에 `session_id` 기반 세션 생성/재접속 골격을 만든다.
2. 상태 변경 이벤트가 들어오면 서버에 최신 스냅샷을 저장하는 최소 저장소를 구현한다.
3. 클라이언트가 끊겼다가 같은 `session_id`로 재접속하면 최신 스냅샷을 반환하도록 한다.
4. 프론트에서는 `연결 끊김 → 재연결 중 → 복구 완료` 상태를 표시한다.
5. 개발자 도구에서 네트워크를 강제로 끊었다가 다시 연결하는 테스트로, 신호등 상태가 유지되는지 확인한다.
