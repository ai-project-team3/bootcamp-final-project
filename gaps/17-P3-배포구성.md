## 왜 공백인가

기획안이 배포를 아예 다루지 않습니다. 참고 레포(Handover_rag)는 **guidelines/5에 배포 계획을 넣어뒀습니다.**

최종발표에서 "왜 이 배포 구성을 골랐나요?"가 나올 가능성이 높고, 단순히 "저렴해서 선택했습니다"는 충분한 근거가 되지 않습니다.

따라서 이번 결정은 **최종 서비스의 장기 운영 인프라가 아니라, 현재 6주 데모/PoC를 안정적으로 발표하기 위한 배포 구성**으로 한정합니다.

**힌트** 검토 완료 — 프론트(React+Vite)는 **Cloudflare Pages 권장**(정적 프론트 배포 및 PR Preview 활용).

백엔드는 **Cloudflare Workers가 기술적으로 불가능해서 제외하는 것이 아닙니다.** Python Workers는 FastAPI를 공식 지원합니다. 다만 현재 프로젝트가 **Python/FastAPI + SQLAlchemy + MySQL/MariaDB + WebSocket** 구조이므로 이를 Workers 런타임에 맞게 전환하려면 데이터베이스 접근 방식과 실시간 세션 구조를 함께 재설계해야 합니다.

따라서 이번 6주 PoC에서는 기존 Python 서버 구조를 최대한 유지할 수 있는 **Railway를 선택**합니다.

Durable Objects는 WebSocket 기반 세션 모델과 잘 맞지만, 이번 프로젝트에서는 기존 FastAPI 구조와 별도의 JS/TS 런타임을 추가하는 복잡성이 있어 채택하지 않습니다.

**남은 결정 — 백엔드 호스팅 한 곳, DO 채택 여부, 코드 프리즈 시점**

# 결정서

## ① 결정

> 한 문장으로. "무엇을 이렇게 한다"

```text
프론트        Cloudflare Pages                 ← 조장 검토 승계

백엔드        Railway (Hobby, $5/월 이상)      ← 이번 결정

DB            Railway 관리형 MySQL             ← 이번 결정

DO            채택하지 않음                    ← 이번 결정

코드 프리즈    중간발표 9/22 · 최종발표 10/17   ← 이번 결정
```

**무료 티어가 아닌 Hobby 유료 플랜을 사용합니다.**

단, Railway Hobby의 $5/월은 리소스 사용량 $5가 포함된 **최소 사용료**이며, 실제 사용량이 이를 초과하면 추가 비용이 발생할 수 있습니다.

이번 결정은 **발표 안정성을 우선한 PoC 배포 결정**입니다.

## ② 근거

> 왜 그렇게 정했나. 조사했으면 출처를 남기세요

### **승계한 것**

프론트 = Cloudflare Pages / 백엔드 = Railway

Cloudflare Workers는 Python Workers에서 FastAPI를 공식 지원하지만, 현재 프로젝트의 기존 **FastAPI + SQLAlchemy + MySQL/MariaDB + WebSocket 구조를 그대로 이전하는 것은 별도의 런타임·DB 접근 구조 검토가 필요합니다.**

따라서 이번 6주 PoC에서는 새로운 런타임으로 구조를 전환하기보다 **현재 Python 백엔드 구조를 유지하면서 배포할 수 있는 Railway를 선택합니다.**

### **🟡 왜 무료 티어를 안 쓰는가 — 이번 결정의 핵심입니다**

```text
Render 무료
→ 15분 동안 inbound traffic이 없으면 서비스 sleep
→ 다시 요청이 들어오면 약 1분 정도 후 재기동

Railway Free
→ 존재함
→ 월 $1의 무료 리소스 크레딧 제공
→ 데모용 상시 실행을 위한 충분한 사용량을 보장하는 플랜은 아님

Railway Hobby
→ $5/월 최소 사용료
→ $5의 월간 리소스 사용량 포함
→ 초과 사용량 발생 시 추가 비용
→ 이번 프로젝트에서는 발표 안정성을 위해 선택
```

발표 시나리오를 고려하면 답이 나옵니다.

```text
발표 순서를 기다린다
       ↓
20~30분 동안 백엔드에 요청이 없음
       ↓
무료 호스팅의 sleep 상태 발생 가능
       ↓
데모 시작 버튼을 누른다
       ↓
서비스 재기동 시간 발생 가능
       ↓
실시간 데모 시작 지연
```

따라서 **무료 플랜의 비용 절감보다 발표 시 안정성을 우선합니다.**

Render 무료 서비스는 15분간 inbound traffic이 없으면 sleep하고, 다시 요청이 들어오면 약 1분 정도 걸려 재기동될 수 있습니다.

Railway 역시 Serverless 기능을 사용하면 서비스를 sleep시킬 수 있으므로, **이번 프로젝트에서는 Serverless를 사용하지 않는 상시 실행 구성으로 운영합니다.**

### **Railway를 고른 이유**

|           | Railway Hobby                      | Render                       |
| --------- | ---------------------------------- | ---------------------------- |
| 무료 플랜     | 있음                                 | 있음                           |
| 이번 선택     | **Hobby $5/월 이상**                  | 선택하지 않음                      |
| Sleep     | **Serverless 미사용 시 sleep 구성하지 않음** | Free는 15분 inactivity 후 sleep |
| WebSocket | 사용 가능                              | 사용 가능                        |
| 기존 구조 유지  | **FastAPI 서버 구조 유지에 적합**           | 가능                           |
| 선택 이유     | **발표 안정성 + 기존 구조 유지**              | Free sleep 회피 시 유료 플랜 필요     |

WebSocket은 장시간 연결을 유지하는 구조이므로, 이번 프로젝트에서는 **서버가 불필요하게 sleep되지 않도록 구성하는 것**이 중요합니다.

따라서 Railway에서는 **Serverless를 활성화하지 않고** 사용합니다.

> ※ Railway가 "무조건 sleep이 없는 서비스"라는 의미가 아닙니다.
> Railway에도 Serverless 기능이 있으므로, **우리 서비스에서는 해당 기능을 사용하지 않는다는 결정**입니다.

### **AWS가 아닌 이유**

AWS는 EC2/ECS 등 다양한 선택지가 있고, 구성에 따라 네트워크·보안·배포 환경을 직접 관리해야 하는 범위가 커질 수 있습니다.

이번 프로젝트는 6주 PoC이므로 인프라 자체를 구축하는 것보다 **애플리케이션 개발과 데모 안정성에 집중하는 것이 우선**입니다.

또한 AWS 프리티어 여부는 계정 생성 시점과 계정 상태에 따라 달라질 수 있으므로, 팀 전체가 동일한 조건으로 사용할 수 있다고 가정하지 않습니다.

⚠️ **팀에 AWS 경험자가 있고 기존 배포 환경을 재사용할 수 있다면 뒤집을 만합니다.**

### **Durable Objects를 안 쓰는 이유**

Durable Objects는 WebSocket 기반의 실시간 세션 관리에 적합합니다.

특히 하나의 Durable Object 인스턴스에서 여러 WebSocket 클라이언트를 조정할 수 있어 **미팅 세션 모델과 기술적으로 잘 맞습니다.**

그러나 이번 PoC에서는 다음 이유로 채택하지 않습니다.

```text
1. 기존 백엔드 구조와 런타임이 달라짐

   백엔드 = Python / FastAPI
   Durable Objects = Cloudflare Workers 기반 JS/TS 환경

   → 기존 서버 구조와 별도의 실행 환경을 추가해야 함


2. 별도의 세션 아키텍처가 필요함

   기존 FastAPI 서버에서 처리하던 세션 상태와
   WebSocket 로직을 Durable Objects 구조에 맞게 재설계해야 함


3. 배포 시 WebSocket 연결 관리 고려가 필요함

   Cloudflare 공식 문서상 Durable Objects의 코드 업데이트 시
   기존 WebSocket 연결이 끊어질 수 있음

   → 발표 직전 배포/핫픽스 시 고려해야 할 제약이 추가됨
```

따라서

> **Durable Objects가 기술적으로 부족해서가 아니라, 현재 6주 PoC에서 얻는 이점보다 기존 구조를 전환하는 비용이 크기 때문에 채택하지 않습니다.**

동시 접속 규모 역시 현재는 **데모 중심의 제한적인 환경**이므로, 별도의 분산 세션 인프라를 도입하기보다 **단일 백엔드 인스턴스 기준으로 구현하고 실제 사용량을 W1 배포 후 확인**합니다.

### **코드 프리즈**

```text
중간발표 9/22(화)
→ 발표 전 안정성 확보를 위해 9/21(월)부터 기능 변경 최소화

최종발표 10/17(토)
→ 최종 리허설을 위해 10/14(수)부터 기능 변경 최소화
```

**프리즈된 코드로 리허설을 해야 리허설이 의미가 있습니다.**

리허설 후 배포하거나 기능을 변경하면 실제 발표 환경과 리허설 환경이 달라질 수 있으므로, 프리즈 이후에는 버그 수정 등 필요한 변경만 허용합니다.

### **비용**

```text
Cloudflare Pages
→ 무료 플랜 범위 내 사용

Railway Hobby
→ 최소 $5/월
→ 약 2개월 기준 최소 약 $10
→ 실제 사용량이 $5/월을 초과하면 추가 비용 발생 가능
```

따라서 기본적인 최소 비용은 약 **$10(약 1.5만원 내외)**로 예상합니다.

단, 이는 **Railway 리소스 사용량이 월 $5 이내라는 가정의 최소 비용**입니다.

**팀 계정 하나로 관리합니다.**

5명이 각각 별도의 배포 계정을 만드는 방식이 아니라, 프로젝트에서 정한 계정을 기준으로 배포 환경과 시크릿을 관리합니다.

## ③ 탈락 대안

> 무엇을 안 골랐고 왜. 최소 하나

### **A. Render 무료 티어**

비용은 0이지만, 15분간 inbound traffic이 없으면 서비스가 sleep하고 다시 요청이 들어오면 약 1분 정도 재기동 시간이 발생할 수 있습니다.

**실시간 데모의 첫 요청 지연 가능성이 있어 발표용 기본 배포로 선택하지 않습니다.**

### **B. Render 유료 플랜**

무료 플랜의 sleep 문제는 사라집니다. 그러나 세 가지에서 Railway Hobby가 앞섭니다 🔍 확인 2026-09-09.

| | Railway Hobby | Render 유료 |
|---|---|---|
| 최소 요금 | **$5/월** | **$7/월** (0.5 CPU / 512MB) |
| 빌드 시간 | **30~90초** | 1~3분 |
| sleep | 없음 (무료 티어 자체가 없음) | 유료 플랜은 없음 |

빌드 시간은 **발표 직전 핫픽스**에서 실질적인 차이가 됩니다.

⚠️ **팀이 Render에 이미 익숙하거나 기존 배포 환경이 있다면 충분히 대안이 됩니다.**
두 플랫폼의 차이는 이 프로젝트 규모에서 결정적이지 않습니다.

### **C. AWS EC2/ECS**

통제력과 확장성은 좋지만, 이번 6주 PoC에서는 인프라 구성과 운영에 들어가는 작업량이 상대적으로 큽니다.

따라서 현재는 애플리케이션 개발에 집중하기 위해 제외합니다.

### **D. Cloudflare Workers + Durable Objects 풀스택**

배포가 가장 단순하고 Durable Objects는 WebSocket 세션 모델과 잘 맞습니다.

**그러나 조장 선행 검토에서 백엔드는 Workers 불가로 판정됐습니다** 🔷 —
Python Workers가 FastAPI는 지원하지만 **직접 소켓 접근이 없어 SQLAlchemy가 MySQL/MariaDB에
붙지 못합니다**(MySQL로 바꿔도 동일). **DB 연결이 안 되면 전환 비용 이전에 성립하지 않습니다.**

여기에 두 가지가 더 걸립니다.

- **언어 분리** — 백엔드는 Python(FastAPI), DO는 JS/TS입니다. 5명 중 DO 담당자만 다른 언어를 쓰게 되고, 그 사람이 빠지면 아무도 못 고칩니다
- **배포 시 활성 WebSocket 절단** — 발표 직전 핫픽스를 원천 봉쇄합니다

**→ 채택하지 않습니다.** 동시 세션이 수십 개를 넘지 않으므로 서버 메모리 + DB로 충분합니다.

### **E. 발표 당일 로컬 실행**

네트워크 의존성을 줄일 수 있다는 장점이 있지만, 실제 배포 환경에서 발생할 문제를 확인할 수 없고 발표 장소의 장비 환경에도 영향을 받습니다.

⚠️ **완전히 배제하지 않습니다.**

배포는 정상적으로 진행하되 **로컬 백업 경로를 리허설에서 함께 검증**합니다.

발표장 네트워크 또는 외부 서비스에 문제가 발생할 경우를 대비한 최종 안전장치로 사용합니다.

## ⑤ 첫 구현 스텝

```text
1. 레포 스켈레톤

   frontend/     React + Vite
   backend/      FastAPI
   decisions/    결정서 및 근거 문서


2. Cloudflare Pages 연결

   frontend/ 빌드 아웃풋 지정


3. Railway 프로젝트 생성

   backend/ 연결
   MySQL 추가
   환경변수 설정


4. ★ "hello" 수준으로 양쪽 배포를 한 번 성공시킨다

   ← W1에 반드시 완료


5. WebSocket 연결 테스트

   브라우저 ↔ FastAPI WebSocket
   연결 / 종료 / 재연결 확인


6. 시크릿 관리 확인

   STT API 키
   DB URL
   기타 환경변수

   → 플랫폼 대시보드에서 관리
   → .env는 Git 제외
```
