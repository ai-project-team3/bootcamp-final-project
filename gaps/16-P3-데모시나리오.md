# 결정서

## ① 결정
> 한 문장으로. "무엇을 이렇게 한다"

**발표의 기본 데모는 전사 Fixture 재생으로 진행하고, 라이브 마이크 입력도 구현하되 발표 기본 경로가 아닌 보조 데모로 쓴다.**

- 전사 Fixture와 라이브 입력은 **동일한 `Utterance` 구조**로 분석 파이프라인에 전달한다
- Fixture는 **`setInterval` 호출 횟수가 아니라 timestamp와 경과 시간을 비교해** 처리할 발화를 결정한다
- 발표 10분 안에 **되돌아감 탐지가 최소 1회 발생**하도록 시나리오를 구성한다
- 핵심 이벤트는 **약 2~4분 구간**에 배치해 발표 흐름과 설명 시간을 확보한다
- 라이브 시연이 실패하면 **즉시 Fixture 데모로 전환**할 수 있게 한다

```text
[데모]                          [최종]
전사 Fixture                    마이크
     ↓                            ↓
                                 STT / 화자 분리
     ↓                            ↓
  Utterance  ←── 같은 구조 ──→  Utterance
     ↓                            ↓
  AI 분석 → 상태 변화 → 화면 표시
```

**공통 데이터 구조** — #15 평가 데이터와 동일

```text
Utterance
├─ timestamp
├─ speaker
└─ text
```

## ② 근거
> 왜 그렇게 정했나. 조사했으면 출처를 남기세요

**1. 데모/PoC의 목표는 핵심 기능의 안정적 재현입니다**
라이브 입력은 최종 서비스의 핵심이지만, 발표 환경에서는 마이크 권한·소음·에코·STT 지연·
네트워크가 결과에 영향을 줍니다. **하나만 터져도 10분 발표에서 회복할 시간이 없습니다.**

**2. 전사 Fixture는 실패 지점을 하나 줄입니다**

```
오디오 Fixture   재생 → STT 호출 → 결과 대기 → 파이프라인
                       ↑ 발표장 네트워크·API 지연·장애가 여기 다 걸림

전사 Fixture     파일 읽기 → 파이프라인
                 ↑ 네트워크 의존 0
```

STT 단계의 외부 의존성을 제거하면서도 **분석 이후의 실제 파이프라인은 그대로 실행**됩니다.
녹화 영상과 달리 "실제로 도는 것"을 보여줄 수 있습니다.

**PoC(`poc/index.html`)가 정확히 이 방식이고 안정적으로 동작했습니다** 🔍 확인 2026-09-08.

**3. 입력 소스만 교체 가능하게 만듭니다**
Fixture와 라이브를 같은 `Utterance` 구조로 연결하면, 데모용 입력을 쓰면서도 최종 서비스에서
**입력 소스만 바꾸면 됩니다.** 파이프라인을 두 벌 만들지 않습니다.

**4. 🔴 Fixture도 안전하지 않습니다 — PoC에서 실제로 겪었습니다** 🔍 확인 2026-09-08

브라우저에서 **탭이 백그라운드가 되면 `setInterval` 이 스로틀**됩니다.
PoC 자동 재생 중 **9초에 8발화만 진행**됐습니다(정상이면 30발화 이상).

> 발표 중 화면을 전환하면 재생이 멈춘 것처럼 보입니다.
> **그래서 호출 횟수가 아니라 timestamp 기반으로 재생 위치를 계산합니다.**

**5. 되돌아감이 반드시 나와야 합니다**
발표에서 보여줄 유일한 기술 차별점입니다. 10분 안에 확실히 나오도록 Fixture를 구성하고,
설명 시간을 확보하기 위해 **2~4분 구간**에 배치합니다.

## ③ 탈락 대안
> 무엇을 안 골랐고 왜. 최소 하나

**A. 발표 전체를 라이브 입력으로 진행**
최종 제품에서는 마이크 → STT 방식을 목표로 합니다. 하지만 발표 전체를 라이브로 하면
마이크 권한·소음·STT 지연·네트워크 등 외부 변수가 발표 결과에 집중됩니다.
**→ 라이브 기능 자체를 포기하는 게 아니라 발표의 기본 입력 경로에서만 제외합니다**

**B. 전체를 녹화 영상으로 재생**
발표 안정성은 가장 높습니다. 하지만 실제 애플리케이션이 입력을 받아 분석하고 상태를 바꾸는
과정을 보여주지 못합니다. **실시간 갱신이 이 제품의 핵심인데 그걸 못 보여줍니다.**
**→ 실제 파이프라인을 실행하는 Fixture 방식으로 결정**

**C. 오디오 Fixture → STT → 분석**
실제 음성을 쓰는 데모가 가능해 인상이 좋습니다. 그러나 STT 과정에서 다시 지연·오류 및
외부 서비스 의존이 발생합니다.
**→ 데모는 전사 Fixture, 오디오 → STT 경로는 라이브 구현에 활용**

> ⚠️ STT 결과를 미리 캐시해두면 네트워크 의존 없이 오디오도 들려줄 수 있습니다.
> **역할 1에 여유가 있으면 뒤집을 만합니다.**
