## 왜 공백인가

§2-4가 **권한만 정하고 접속을 안 정했습니다.** 동석자가 같은 미팅에 어떻게 붙나요 — 방 코드, 초대 링크, 로그인?

**힌트** 발표 데모에서 2인 접속을 보여줘야 하니 가장 단순한 방식이 유리

---

# 결정서

## ① 결정
> 한 문장으로. "무엇을 이렇게 한다"

**데모/PoC에서는 발표자 화면에 표시된 6자리 방 코드를 동석자가 입력해 백채널에 접속한다.**

- 로그인·초대 링크는 사용하지 않는다
- 코드 입력 성공 시 **짧은 수명의 `joinToken`** 을 발급한다
- 방 코드와 토큰은 미팅 종료와 동시에 폐기한다
- **백채널은 원본 음성이 아니라 분석 결과·상태·지원 정보를 공유한다** (#13과 같은 결정)
- 최종 서비스에서는 사용자 인증·초대·역할별 권한으로 확장할 수 있도록 세션 단위로 설계한다

**접속 흐름**

```text
발표자 세션 생성
      ↓
6자리 방 코드 발급
      ↓
발표자 화면에 코드 표시
      ↓
동석자 코드 입력
      ↓
임시 joinToken 발급
      ↓
백채널 접속
      ↓
분석 결과 / 상태 / 지원 정보 공유   ← 음성은 전송하지 않음
```

## ② 근거
> 왜 그렇게 정했나. 조사했으면 출처를 남기세요

**1. 데모/PoC 범위에 맞습니다**
현재 목표는 최종 서비스가 아니므로 회원·팀·초대 시스템까지 구현하는 것은 핵심 기능 검증에 비해
범위가 큽니다. 지금 제품에 계정·팀 개념 자체가 없습니다.

**2. 발표에서 가장 빠릅니다**
2인 접속을 보여줘야 하는데 로그인이 들어가면 화면이 두 번 넘어갑니다. 6자리 코드는 숫자 입력이
전부이고 **말로도 전달됩니다.**

**3. 세션 상태가 이미 서버에 있습니다**
§2-4가 세션 상태를 서버에 두기로 했으므로 `방 코드 → 세션 id` 매핑 하나만 추가하면 됩니다.

**4. 🔴 다만 방 코드는 법적·보안적 통제 장치가 아닙니다**

코드는 전화로 불러줄 수 있으므로 **동석 여부를 기술적으로 검증하지 못합니다.**
따라서 "방 코드를 쓰니까 원격 접속이 막힌다"고 해석하면 안 됩니다.

**실효적인 통제는 #13에서 정한 대로 "백채널에 음성을 보내지 않는 것"입니다.**
대법원 2023도8603이 '청취'를 **대화 도중 실시간으로 듣는 행위**로 확정했으므로,
음성을 전송하지 않으면 청취가 성립하지 않습니다 🔍.

기획안 §2-4의 백채널 설계(신호등 공유 + 탭 신호)는 원래 음성이 필요 없으므로
이 제약이 기능을 깎지 않습니다.

**5. 최소한의 접근 제어는 둡니다**
`joinToken` 수명 제한, 코드 입력 횟수 제한, 세션 ID를 그 자체로 접근 권한으로 쓰지 않기 —
데모 수준에서 감당 가능한 범위입니다.

## ③ 탈락 대안
> 무엇을 안 골랐고 왜. 최소 하나

**A. 초대 링크 방식**
카카오톡·Slack으로 전달할 수 있어 사용자 경험은 편리합니다. 그러나 별도 초대 URL 생성·관리
흐름이 필요하고, 대면 미팅에서 폰을 꺼내 메신저를 여는 동작이 코드 입력보다 느립니다.
**→ 데모에서는 6자리 코드로 결정**

**B. 로그인 + 팀 목록 방식**
인증과 팀 단위 권한 관리가 가능합니다. 하지만 회원가입·로그인·팀 생성·구성원 관리·초대까지
구현 범위가 커집니다.
**→ 최종 서비스 확장 사항으로 보류**

**C. QR 코드 방식**
모바일에서 빠르게 접속할 수 있습니다. 다만 QR도 전달·공유가 가능하므로 **동석 여부를
기술적으로 보장하지 못하는 것은 방 코드와 같습니다.** 그리고 발표자 화면에 QR을 띄우면
화면②의 요소가 하나 늘어납니다(현재 4개).
**→ 구현과 발표 설명이 더 단순한 6자리 코드로 결정**

> ⚠️ 화면 배치를 짜다가 QR이 낫다고 판단되면 뒤집어도 됩니다. **서버 쪽 설계는 동일합니다.**

## ④ 계약 영향
> P0 4개(화자 분리 / 항목 풀 스키마 / 상태 전이표 / 미팅 연결키)를 건드리나?

- [ ] 건드리지 않음 — 담당자가 결정합니다
- [x] **P0 계약을 건드립니다 — 결정하지 말고 조장에게 올립니다**

| P0 | 어떻게 |
|---|---|
| **미팅 연결키** | 세션 생성 시 `roomCode` 발급. **고객 정보가 아니라 미팅 세션 단위의 임시 접속 정보** |

**세부**

- 코드 입력 성공 시 짧은 유효시간의 `joinToken` 발급
- 미팅 종료 시 `roomCode` · `joinToken` 무효화
- 코드 입력 횟수 제한 등 최소한의 접근 제어
- **세션 ID 자체를 백채널 접근 권한으로 사용하지 않음**

**그 밖에**

- **#13과 같은 결정입니다** — 백채널에 음성을 전송하지 않습니다
- 역할 5(미팅↔고객 연결)와 구분 — `roomCode` 는 **세션 단위이고 고객 단위가 아닙니다**

**최종 서비스 확장 경로**

```text
데모        6자리 roomCode  →  임시 접속
최종        로그인  →  팀/사용자 확인  →  역할별 권한  →  세션 접근
```

## ⑤ 첫 구현 스텝
> 이 결정대로면 W1(9/14~)에 내가 무엇부터 만드나

**W1**

- 세션 생성 시 6자리 `roomCode` 발급 + 중복 확인
- 발표자 화면에 방 코드 표시
- 동석자용 코드 입력 화면

**W3**

- `roomCode` 검증 후 짧은 수명의 `joinToken` 발급
- WebSocket 연결 시 `joinToken` 으로 백채널 참여
- **분석 결과·상태 정보만 동석자 화면에 전달되는지 확인 (음성 미전송 검증)**

**W5**

- 미팅 종료 시 코드·토큰 폐기
- 잘못된 코드 반복 입력 제한
- 발표자 → 동석자 접속 → 정보 수신 → 미팅 종료까지 전체 흐름 리허설

> ⚠️ **미확인** — 2인 동행 미팅이 실제로 얼마나 되는지 모릅니다. 드물면 백채널을
> "내 노트북 + 내 폰"용으로 재정의해야 하고 방 코드 설계도 달라집니다.
> **#5 현업 인터뷰 항목으로 넣어야 합니다.**
