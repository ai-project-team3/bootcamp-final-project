## 왜 공백인가

발화가 끝나고 **몇 초 안에 신호등이 바뀌어야 "실시간"인지** 목표가 없습니다. 목표가 없으면 역할 1·2·3이 각자 다른 전제로 설계합니다.

**힌트** 제안 — 발화 종료 → 신호등 반영 3초, 카드 갱신 5초. 실측 후 조정

# 결정서

## ① 결정
> 한 문장으로. "무엇을 이렇게 한다"

**발화 종료 시점부터 신호등 상태 반영까지 p95 3초 이내, 카드 갱신까지 p95 5초 이내를 1차 목표로 두고, 두 지연을 분리 측정한다.**

## ② 근거
> 왜 그렇게 정했나. 조사했으면 출처를 남기세요

- 기획안의 힌트가 이미 **신호등 3초 / 카드 5초**를 초기 제안값으로 두고 있어, W1부터 역할 1·2·3이 같은 기준으로 설계하기에 가장 안전하다.
- 이 서비스의 핵심은 먼저 **상태 변화가 실시간으로 보이는 것**이고, 카드 생성은 그 상태 변화 이후에 따라오는 보조 기능이다. 따라서 두 기능을 하나의 지연 목표로 묶기보다 각각 측정하는 편이 구조에 맞다.
- 평균값만 보면 일부 느린 구간이 가려질 수 있으므로, 발표와 데모에서 실제 체감에 가까운 **p95**를 공식 지표로 사용한다.
- 측정 시작점은 공통적으로 `utterance_end`로 두고, 최소한 `state_rendered`, `card_rendered`까지의 시간을 기록한다.
- 목표값은 우선 고정하되, W1~W3 실측 결과에서 구조적으로 달성이 어렵다는 근거가 나오면 팀에 공유한 뒤 조정한다.

## ③ 탈락 대안
> 무엇을 안 골랐고 왜. 최소 하나

1. **지연 목표 없이 구현 후 측정만 하는 안**
   - 역할 1·2·3이 서로 다른 전제로 최적화할 수 있고, 통합 시점에 병목을 뒤늦게 발견할 가능성이 크다.
   - 최종 발표에서 "실시간"이라고 부르는 기준을 수치로 설명하기 어렵다.

2. **신호등과 카드를 모두 동일한 3초 목표로 두는 안**
   - 카드에는 LLM 생성 시간이 포함되어 상태 갱신보다 변동폭이 크다.
   - 핵심 상태 반영과 생성 기능을 같은 SLA로 묶으면 불필요하게 구현 난도가 올라간다.

3. **평균 지연만 기록하는 안**
   - 일부 큰 지연이 평균에 가려질 수 있어 데모 안정성과 실제 체감을 제대로 반영하지 못한다.

- [x] 건드리지 않음 — 담당자가 결정합니다

**판단 근거:** P0의 화자 분리 방식, 항목 풀 스키마, 상태 전이 규칙, 미팅 연결키의 의미를 바꾸지 않고 기존 파이프라인에 성능 측정 기준만 추가한다.  
단, 공통 fixture에 새로운 타임스탬프 필드를 필수 계약으로 추가해야 한다면 조장에게 먼저 공유한다.

## ⑤ 첫 구현 스텝
> 이 결정대로면 W1(9/14~)에 내가 무엇부터 만드나

1. 공통 타임스탬프 지점을 정의한다: `utterance_end`, `stt_final`, `match_done`, `state_updated`, `state_rendered`, `card_rendered`.
2. fixture 재생 경로에 타이밍 로거를 붙인다.
3. 구간별 지연과 E2E 지연을 기록하고 p50/p95를 출력하는 간단한 측정 스크립트를 만든다.
4. W1에는 3초/5초 달성 자체보다 **어느 단계에서 시간이 소비되는지 보이는 상태**를 우선 만든다.
5. W3 실시간 연결 후 동일 측정 기준으로 실제 오디오 기준 p95를 다시 기록한다.
