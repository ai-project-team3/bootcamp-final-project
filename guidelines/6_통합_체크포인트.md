### 왜 앞으로 당겼나 (수정, E-3)

전원이 **바이브코딩**으로 작업한다. 보일러플레이트 · 화면 · CRUD를 쓰는 시간은 크게 줄지만
**재고 고치는 시간은 줄지 않는다** — 스파이크 실측, 라벨링, 튜닝, 통합 디버깅은 그대로다.

그래서 **쓰는 일을 앞으로 당기고, 재고 고치는 일에 시간을 몰아준다.**

| | 이전 | 지금 | 얻는 것 |
|---|---|---|---|
| fixture 관통 | W1 금 | **W1 수** | 이틀 |
| 실시간 1회 | **W3** | **W1 금** | **2주** |
| 중간발표 데모 | fixture 재생 | **실시간** | 발표의 격 |
| 재발 재현율 첫 측정 | W3 금 | W3 금 (동일) | **W3 전체가 순수 품질 작업** |

가장 큰 변화는 **W3이 통째로 튜닝 기간이 된다**는 것이다. 이전 계획은 W3에 실시간을 붙이면서
동시에 재발을 측정해야 했다. 이제 실시간은 이미 돌고 있다.

### ① 1층 반대사유 풀이 아직 없다

`#8`이 낸 39개는 **1층이 아니다.**

| 카테고리 | 개수 | 실제 층 |
|---|--:|---|
| A 오프닝/라포 | 3 | 2층 후보 |
| B 니즈분석-기본정보 | 7 | 2층 후보 |
| C 니즈분석-리스크 | 6 | 2층 후보 |
| D 상품설명 | 8 | **2층** (금소법) |
| **E 반론처리** | **5** | **1층 ← 이것뿐** |
| F 청약/클로징 | 6 | 2층 후보 |
| **G 컴플라이언스** | **4** | **2층** (3대 기본지키기) |

이 분류대로면 **2층이 34개**가 되어 `2번 문서`의 12개 상한을 크게 넘는다.

**해야 할 일**
**분량은 약 480문장이다** (수정, E-2) — `aliases` 210 + 슬롯 `cues`·`blockers` 약 270.
**1일차에 항목 ID와 `aliases`(210)까지 끝내 역할 2를 먼저 풀어주고**, 슬롯 예문은 2~4일차에 채운다.

- **E 5개를 세분화해 1층 반대사유 30개**를 만든다 — 보험료 부담 / 필요성 의문 / 타사 비교 /
  가족 상의 / 가입 시기 / 건강 고지 우려 / 해지 손실 우려 / 설계사 신뢰 / 기존 보험 중복 …

- A·B·C·F는 **1차에서 제외**한다. 상담 프로세스이지 반대사유도 법정 필수도 아니다

## 6-4. E2E 시나리오 — 제출 전 반드시 통과

W3 금요일부터 매주 돌린다.

```
1.  딜 생성 → 템플릿 선택 (보험 상담)
2.  1차 미팅 시작 → "이번 미팅 기본 체크" 5개가 뜬다 (지난번 미해결 아님)
3.  fixture 재생 → 발화가 Utterance로 들어온다
4.  반대사유 항목이 🔴로 켜지고 근거 발화가 붙는다
5.  슬롯이 채워져 🟡 → 🟢으로 오른다
6.  blocker 발화가 나와 🟢 → 🔴로 내려간다  ← 재발 사건 1건 기록
7.  필수 항목이 자동 체크되고, 전부 채워지면 가운데 열이 접힌다
8.  카드 1·2순위가 매 턴 갱신된다
9.  동석자가 방 코드로 접속해 항목을 탭 → 6초 배너
10. 미팅 종료 → 언급 확인 화면 → 리포트(1차 = discovery)
11. 같은 딜로 2차 미팅 시작 → 1차 미해결이 색 그대로 이월되고 (이월) 스티커가 붙는다
12. 2차 리포트가 change 유형으로 나오고 연속 미해결이 표시된다
13. 네트워크를 강제로 끊었다 붙여도 상태가 유지된다
14. 평가 러너를 돌려 지표 표가 나온다
```

**6번과 11번이 이 제품의 전부다.** 나머지가 다 돼도 이 둘이 안 되면 발표할 게 없다.

## 6-6. 평가 데이터 계획 (`#15`)

```
목표 재발 사례        40건
세션당 심는 수         2건    ← PoC 실측 상한. 3건 이상은 부자연스럽다
                    ─────
양성 세션             20세션
+ 음성 대조군          5세션   ← 재발 0건. 오탐 측정용
                    ─────
총                   25세션 × 12분 = 300분
작업량                약 40 person-hour → 5명이면 1인당 8시간
```

**라벨링**: 전량 1명이 하고 **20%(5세션)를 2명이 독립 라벨링**해 Cohen's κ를 계산한다.
평가 단위는 **발화**다.

| 지표 | PoC 목표 |
|---|---:|
| 재발 재현율 | **≥ 0.80** |
| 재발 정확도 · F1 | 함께 측정 |
| Cohen's κ | ≥ 0.61 |

🔴 **"심어서 측정했다"를 발표에서 먼저 말한다.** 자연 발생만 기다리면 50세션 이상이 필요해
6주에 불가능하다. 숨기면 Q&A에서 깨지고, 먼저 말하면 방법론을 안다는 신호가 된다.
목표값은 **최종 서비스 성능 보증이 아니라 PoC 목표**다.

### ⚠️ #9 — 사후 연결과 이월 무효화 (신설, E-1)

`2번` §2-5의 한 줄에 아직 답이 없다.

> *"`deal_id`가 `None`인 미팅은 1차처럼 동작하고, 나중에 연결하면 `seq`가 재계산된다."*

| 물음 | |
|---|---|
| 사후 연결로 `seq`가 3차가 되면 | **이미 기록된 `StateChange`는 어떻게 되나** |
| `unlink` 하면 | 심어둔 `trigger="carryover"` 행을 **지우나, 취소 이벤트를 덧붙이나** |
| 이월이 철회되면 | **"지표에서 제외"가 무슨 뜻이 되나** |

**리플레이**(로그를 다시 계산) 대 **보상 이벤트**(취소 행을 덧붙임) 중 하나를 고른다.
이벤트 로그를 정본으로 둔 구조라 이 선택이 §2-3 전체에 걸린다. **W3에 결정하고 `2번`에 반영한다.**
