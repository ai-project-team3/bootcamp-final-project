## 2-1. `Utterance` — 파이프라인의 입구

`backend/app/schemas/utterance.py`

```python
class Utterance(BaseModel):
    id:         str
    meeting_id: str
    speaker:    Literal["me", "them", "unknown"]
    text:       str
    t_start:    float            # 미팅 시작 기준 초
    t_end:      float
    confidence: float            # 0.0 ~ 1.0 — 화자 판정 신뢰도
```

**모든 입력 소스가 이 구조를 낸다.** 화상 2채널도, 대면 화자 등록도, 데모 fixture도 같다.
입력 소스를 바꿔도 아래 파이프라인은 그대로다.

| 소스 | `confidence` |
|---|---|
| `DualChannelSource` (화상 · MVP) | 항상 `1.0` — 채널이 물리적으로 나뉨 |
| `EnrolledVoiceSource` (대면 · W4) | 임베딩 유사도 기반 |
| `FixtureSource` (데모 · 평가) | 라벨에 있는 값 |

🔒 **`speaker != "them"` 이거나 `confidence`가 임계값 미만이면 상태 전이를 일으키지 않는다.**

## 2-2. 템플릿 — YAML로 쓰고 Pydantic으로 읽는다

`backend/app/schemas/template.py`

```python
class Slot(BaseModel):
    """항목의 해결 조건 한 칸. 역할 3이 쓴다."""
    key:      str              # "amount"
    label:    str              # "금액"
    cues:     list[str]        # 충족됐다고 볼 예문 3개
    blockers: list[str] = []   # 취소됐다고 볼 예문 3개 — 재발 판정용

class Item(BaseModel):
    """전역 항목 카탈로그의 한 줄. 템플릿을 넘어 ID가 안정적이다."""
    id:       str              # "budget_approval" — 영문 snake_case
    label:    str              # "예산 승인" — 한국어
    aliases:  list[str]        # 이 항목 얘기가 나왔다고 볼 예문 5개
    keywords: list[str] = []
    slots:    list[Slot]       # 1층 1~4개 / 2층 0개

class TemplateItem(BaseModel):
    item_id:    str
    layer:      Literal[1, 2]   # 1 반대사유 / 2 필수 항목
    default_on: bool
    priority:   int             # 낮을수록 위

class Template(BaseModel):
    id:    str
    label: str
    items: list[TemplateItem]
```

**`id`는 영문 snake_case, `label`은 한국어.**
`id`는 fixture JSON·DB·모듈 간 계약에 쓰이는 기계용 식별자이고, `label`은 화면에 뜨는 이름이다.

### 검증 규칙 (로드 시 강제)

| 규칙 | 위반하면 |
|---|---|
| `item_id`가 카탈로그에 존재 | 로드 실패 |
| 템플릿 안에서 `item_id` 중복 금지 | 로드 실패 |
| **2층은 `default_on=true` 강제** | 로드 실패 |
| **2층은 템플릿당 12개 이하** | 로드 실패 — 대분류로 합쳐라 |
| **2층은 `slots` 비어 있어야 함** | 로드 실패 |
| `aliases` 최소 3개 (권장 5개) | 로드 실패 |
| **1층 `slots`는 1~4개** | 로드 실패 — 항목을 쪼개라 |
| `default_on=true`인 1층은 3~7개 | 경고 |

**검증 규칙이 조기 경보를 겸한다.** 슬롯이 5개를 넘거나 2층이 12개를 넘으면
항목 정의가 잘못됐다는 신호다.

### 목록에 없는 발화

```python
class OffListMention(BaseModel):
    meeting_id: str
    t:          float
    raw:        str      # 원문 그대로. 분류하지 않는다
```

예약 항목 `_other` 하나에 쌓는다. 리포트에만 원문으로 나온다.

## 2-3. 상태 — 변화 리스트가 정본이다

`backend/app/schemas/state.py`

```python
State = Literal["unseen", "raised", "partial", "resolved"]
RANK  = {"unseen": 0, "raised": 1, "partial": 2, "resolved": 3}

class StateChange(BaseModel):
    id:         str
    meeting_id: str
    item_id:    str
    at:         float          # 미팅 내 시각(초). 이월은 0.0
    from_st:    State
    to_st:      State
    trigger:    str            # 근거 발화 원문 | "carryover" | "manual"
    utterance_id: str | None
```

🔒 **항목의 현재 상태를 따로 저장하지 않는다. 변화 리스트에서 파생한다.**

| 파생 | 방법 |
|---|---|
| 현재 상태 | 마지막 변화의 `to_st` |
| **재발** | `RANK[to_st] < RANK[from_st]` 인 변화 |
| 화면 ② 타임라인 | 리스트 그 자체 |
| 차수 이력 | 차수별 리스트를 이어 붙임 |

**`trigger`가 `carryover` 또는 `manual`인 변화는 모든 지표에서 제외한다.**

### 상태는 슬롯 충족으로 파생된다 (1층만)

| 슬롯 충족 | 상태 |
|---|---|
| 0개 | `raised` 🔴 |
| 일부 | `partial` 🟡 |
| 전부 | `resolved` 🟢 |

### 전이표 🔒

| 현재 | 사건 | 다음 | 재발 |
|---|---|---|:--:|
| `unseen` | 매칭, 슬롯 0충족 | `raised` | |
| `unseen` | 매칭, 슬롯 일부 | `partial` | |
| `unseen` | 매칭, 슬롯 전부 | `resolved` | |
| `raised` | 슬롯 일부 충족 | `partial` | |
| `raised` | 슬롯 전부 충족 | `resolved` | |
| `partial` | 슬롯 추가 충족 | `resolved` | |
| `partial` | 슬롯 전부 취소 | `raised` | ✅ |
| `resolved` | 슬롯 일부 취소 | `partial` | ✅ |
| `resolved` | 슬롯 전부 취소 | `raised` | ✅ |
| 모든 상태 | 사용자 수동 변경 | 지정값 | ❌ |

**규칙 다섯**

1. `unseen`으로는 돌아가지 않는다
2. 상태가 내려가면 전부 재발이다 (`resolved`→`partial` 포함)
3. `speaker != "them"` 또는 `confidence` 미달 발화는 전이를 일으키지 않는다
4. `trigger == "manual"` 은 지표에서 제외한다
5. **마지막 상승 이후 30초 안의 재등장은 재발로 보지 않는다** — 같은 턴의 연장이다.
   ⚠️ 30초는 초기값. W3에 fixture로 확정한다

### 재발

```python
class Recurrence(BaseModel):
    scope: Literal["within_meeting", "cross_meeting"]
```

| 범위 | 무엇 | 측정 |
|---|---|---|
| `within_meeting` | 한 미팅 안에서 상태가 내려감 | **사건 검출** — 재현율·정확도 ★ |
| `cross_meeting` | 1차 `resolved` → 2차 `raised` | 차수별 최종 상태 비교로 파생 |

**역할 3의 핵심 지표는 `within_meeting` 재현율이다.**

## 2-4. 필수 항목 — 별도 모델

`backend/app/schemas/checklist.py`

```python
class ChecklistState(BaseModel):
    meeting_id:   str
    item_id:      str
    mentioned:    bool                  # 자동 감지
    mentioned_at: float | None
    evidence:     str | None            # 근거 발화 원문
    confirmed:    bool = False          # 미팅 종료 화면에서 사람이 확인
    confirmed_at: datetime | None
```

🔒 **2층은 신호등이 아니다.** 상태가 2개(☐/☑)이고 단조 증가하며 재발이 없다.

🔒 **`mentioned`는 "언급됨"이지 "완료"가 아니다.** 화면 라벨도 `필수 항목 · 언급 여부`다.
`완료`라고 표시하면 오탐이 사용자를 안심시켜 법정 의무 미이행을 만든다.

**리포트에는 `mentioned`와 `confirmed`를 구분해 기록한다.** 금소법 대응 근거가 필요할 때
이 구분이 값어치를 한다.

## 2-5. 딜과 미팅

`backend/app/schemas/deal.py`

```python
class Deal(BaseModel):
    id:           str
    label:        str            # "A사 신규 도입" / "김OO님 종신보험"
    template_id:  str
    counterpart:  str            # 표시용 상대 이름
    company:      str | None     # 개인 영업이면 없음
    external_ref: str | None     # 나중에 CRM ID 넣을 자리
    voice_ref:    str | None     # 상대 임베딩 (대면 모드 재사용)
    created_at:   datetime

class Meeting(BaseModel):
    id:              str
    deal_id:         str | None  # None = 아직 연결 안 됨
    seq:             int         # 차수 — 딜 안에서 자동 부여
    template_id:     str
    recording_notice: bool       # 녹음 안내 체크 여부
    session_id:      str         # 재접속용. deal_id와 분리
    started_at:      datetime
    ended_at:        datetime | None
```

🔒 **연결 단위는 딜(건)이다.** 회사도 사람도 아니다 — 참석자가 바뀌어도 딜은 유지된다.

**`seq`는 자동이다.** 딜에 묶인 미팅을 시간순으로 세면 나온다. `deal_id`가 `None`인
미팅은 1차처럼 동작하고(이월 없음), 나중에 연결하면 `seq`가 재계산된다.

**`session_id`는 `deal_id`와 분리한다.** 재접속 키를 연결 키로 쓰면 세션이 딜에 묶여버린다. (`#12`)

`voice_ref`는 `#1`과 물린다 — 대면 모드에서 1차에 등록한 상대 목소리를 저장해두면
**2차부터는 등록 구간이 필요 없다.**

## 2-6. 카드

`backend/app/schemas/card.py`

```python
class Card(BaseModel):
    meeting_id: str
    rank:       Literal[1, 2]    # 1순위 · 2순위. 3순위는 만들지 않는다
    item_id:    str
    evidence:   str              # 근거 발화 원문
    evidence_t: float
    script:     str | None       # LLM이 쓴 제안 문장. 1순위만
    created_at: float
```

🔒 **후보는 신호등 상태에서 규칙으로 뽑는다. LLM은 `script` 한 줄만 쓴다.**
**카드는 매 턴 새로 만들고 버린다.** 저장은 리포트용 이력으로만 한다.

**2순위는 `item_id`만 노출한다.** 같은 크기로 두면 미팅 중에 둘을 비교하게 되고,
그 비교 비용이 카드의 목적(빠른 행동)을 깎는다.

## 2-7. 백채널

`backend/app/schemas/backchannel.py`

```python
class BackchannelSignal(BaseModel):
    meeting_id: str
    item_id:    str          # 동석자가 탭한 항목
    text:       str          # 항목에서 자동 생성된 정문구
    at:         float
    reflected:  bool = False # 발표자가 그 항목을 이어서 다뤘는가
```

🔒 **원본 음성을 전송하지 않는다.** 동석자에게는 상태와 신호만 간다. (`1` §1-5 ⑦)

동석자는 **6자리 방 코드**로 들어오고, 코드 입력에 성공하면 **짧은 수명의 `joinToken`**을 받는다.
방 코드와 토큰은 미팅 종료와 동시에 폐기한다. (`#14`)

## 2-8. 지연 측정

`backend/app/schemas/timing.py`

```python
class TimingMark(BaseModel):
    meeting_id:   str
    utterance_id: str
    stage: Literal[
        "utterance_end", "stt_final", "match_done",
        "state_updated", "state_rendered", "card_rendered",
    ]
    at: float
```

**목표** (`#9`)

| 구간 | p95 목표 |
|---|---|
| `utterance_end` → `state_rendered` | **3초** |
| `utterance_end` → `card_rendered` | **5초** |

**두 지연을 분리 측정한다.** 카드에는 LLM 생성 시간이 포함되어 변동폭이 크다.
평균이 아니라 **p95**를 공식 지표로 쓴다.
