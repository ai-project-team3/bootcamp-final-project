# 역할 배정 희망표

> 역할은 다섯입니다. **역할 5는 조장이 맡고, 나머지 네 자리를 네 명이 나눕니다.**
> 다섯 개 전부 실었습니다 — 서로 어떻게 물리는지 알아야 하니 다 읽어주세요.
>
> ✅ **취합 완료 — 배정안은 [`역할_배정_결과.md`](역할_배정_결과.md) 에 있습니다.**
> 이 문서는 각 역할이 무슨 일을 하는지 설명한 원본으로 남겨둡니다.

---

## 어떻게 정하나

1. 각자 **1지망 · 2지망**과 이유를 적습니다
2. 겹치면 조장이 조율합니다 — 희망을 우선하되 프로젝트 리스크를 함께 봅니다
3. 조장이 **오늘 취합·조율**하고, 9/14(월) 계약 동결 회의에서 확정합니다

---

## 먼저 알아야 할 것

**① 각자 백엔드와 자기 화면을 함께 가집니다.**
"프론트 담당"이라는 자리를 두지 않았습니다. 자기 기능의 화면은 자기가 만듭니다.

**② 각자 지표를 하나씩 소유합니다.** 이게 배정의 기준입니다.

**③ 여러분의 무대는 발표가 아니라 Q&A입니다.**

```
발표 10분     조장 단독. 문제 · 차별점 · 데모 · 지표 한 장
              → 기술 상세를 넣기엔 너무 짧습니다

Q&A 20~30분   팀 전체가 나갑니다
              → 아키텍처, 모델, 측정 방법은 전부 여기서 나옵니다
              → 질문이 오면 담당자가 직접 답합니다
```

**발표의 2~3배가 Q&A입니다.** 기술 역량이 드러나는 자리는 사실상 여기뿐이고,
질문별 답변자를 미리 배정해두면 **네 명이 전부 노출됩니다.** 배정표는 문서 끝에 있습니다.

**④ W5에 각자 "내 지표를 올린 개선 하나"를 만듭니다.**
> *"0.72에서 시작했는데 ○○를 해서 0.81이 됐습니다"*

Q&A에서 가장 강한 답변 형태입니다. 절대값보다 이게 셉니다.

# 역할 1 — 음성 · 실시간

> **소리를 발화로 바꿔 흘려보낸다.** 파이프라인의 입구.

## 하는 일

| 주차 | |
|---|---|
| **W1** | 브라우저에서 **내 마이크와 상대 목소리를 각각 따로** 받는 스파이크. `SpeakerSource` 인터페이스 확정. **스켈레톤 — `main.py` 뼈대 + 빈 라우터로 서버가 켜지는 상태 + 첫 배포 1회 성공.** WebSocket 에코 서버. 지연 측정용 타임스탬프 6지점 |
| **W3** | STT 실연결 · 오디오 청킹. 목표는 **"fixture와 똑같은 JSON을 실시간으로 뱉기"** |
| **W4** | 백채널 전송 · 네트워크 끊김 복구 · 방 코드 접속 |
| **W5** | 지연 p95 측정·개선 · **발표 전 배포 안정화** |

**공통 셸도 소유합니다** — 디자인 토큰, WebSocket 클라이언트, 레이아웃.

**배포도 소유합니다.** Cloudflare Pages(프론트) + Railway(백엔드·DB) —
`guidelines/5-6`이 구성은 정해뒀고, 연결과 운영이 이 자리 몫입니다.
Railway는 **Serverless를 끄고 상시 실행**해야 합니다. WebSocket이 장시간 연결을 유지하는 구조라
sleep되면 발표 중에 끊깁니다 — 이게 배포가 역할 1에 붙는 이유입니다.

> 부담이 커 보이지만 **W1에 한 번 성공시키면 이후는 push만 하면 됩니다.**
> 둘 다 GitHub 연동 자동 배포라 상시 노동이 아니라 초기 설정입니다.

## 필요한 것

브라우저 오디오 API · WebSocket · 성능 프로파일링. **가장 "인프라 엔지니어링"스러운 자리.**

## 어필점

> **개발** *"실시간 음성 스트리밍 파이프라인 설계·구축, p95 지연 N ms"*
> **개발** *"FastAPI 백엔드 배포·운영 — 상시 연결 환경에서 무중단 데모 2회"*

지표가 셋이라 말할 거리가 많습니다 — WER · p95 지연 · 드롭률.
그리고 **"모델을 안 쓰고 문제를 없앴다"** 는 서사가 있습니다. 화자 분리를 ML로 푸는 대신
채널을 물리적으로 나눠 정확도를 100%로 만든 판단입니다.

## Q&A에서 답할 것

- **"실시간이라는데 몇 초 걸려요?"** → p95 3초. **구간별로 분해해서** 답변
- **"화자 분리 어떻게 하셨어요?"** → 모델 안 썼습니다. 채널을 나눴고 왜 그게 더 정확한지
- **"대면에서도 되나요?"** → MVP는 화상만. **시장 판단이 아니라 난제를 하나로 유지한 선택**
- **"네트워크 끊기면요?"** → 서버가 기준. 상태 변화마다 즉시 저장하고 재접속하면 복구
- **"배포는 어디에 하셨어요?"** → Cloudflare Pages + Railway. **무료 티어를 왜 안 썼는지**
- **"발표 중에 서버가 죽으면요?"** → 코드 프리즈 날짜와 상시 실행 구성

## 알고 고르세요

🔴 **W1 첫날 스파이크가 실패하면 MVP 전제가 무너집니다.** 탭 오디오에 내 목소리가 섞이면
2채널 분리가 성립하지 않습니다. **부담이 앞쪽에 몰려 있습니다.**

🔴 **네 자리 중 W1이 가장 무겁습니다.** 스파이크 + 스켈레톤 + 첫 배포가 한 주에 겹칩니다.
다만 스켈레톤은 WebSocket 에코 서버와 사실상 같은 작업이라 실제 추가분은 배포 1회입니다.

W3이 최고조입니다 — 여기서 막히면 전체가 밀립니다.

**안 맞는 사람**: 남이 기다리는 상태에서 일하는 게 부담스러운 사람.

# 역할 2 — 항목 매칭

> **이 말이 어느 항목인지 맞힌다.** 프로젝트의 실제 병목.

## 하는 일

| 주차 | |
|---|---|
| **W1** | 임베딩 모델 스파이크. 표현사전 기반 매처 v0 + fixture로 **F1 첫 측정**. 매칭 검수·라벨링 화면 |
| **W3** | 임베딩 하이브리드 · 임계값 곡선 · **차단 신호(blocker) 매칭 연결** |
| **W4** | 목록에 없는 발화 처리 · 오분류 튜닝 · 라벨링 결과 자동 적재 |
| **W5** | F1 최종 수치 |

**검수·라벨링 화면을 소유합니다** — 팀 전원의 라벨링이 이 도구 위에서 돕니다.

## 필요한 것

임베딩 · 검색·랭킹 · 임계값 튜닝. **가장 "ML·데이터"스러운 자리.**

## 어필점

> **개발** *"표현사전+임베딩 하이브리드 검색기 구현, 매칭 F1 0.NN"*

**여기가 재발 탐지의 실제 병목입니다.** *"근데 위에서 좀…"* 을 `승인 절차 차단 신호`로
잡아내야 재발이 탐지됩니다. 못 잡으면 상태 판정이 아무리 정확해도 **재현율이 0**입니다.

그리고 **데이터 플라이휠**을 만듭니다 — 수기 예문은 5개만 쓰고, 팀이 라벨링할수록
표현 사전이 자동으로 두꺼워지는 구조입니다.

## Q&A에서 답할 것

- **"매칭 정확도가 어떻게 되나요?"** → F1 + **임계값 트레이드오프 곡선**
- **"표현 사전은 사람이 다 썼어요?"** → 씨앗 5개만. 라벨링이 사전을 키우는 구조
- **"모르는 말이 나오면요?"** → 억지로 붙이지 않고 `기타`에 원문 그대로. **왜 그게 안전한지**
- **"임베딩 모델은 뭘 쓰셨어요?"** → 선택 근거와 한국어 성능 실측

## 알고 고르세요

🔴 **네 자리 중 기술 난이도가 가장 높습니다.** 성과가 숫자로 바로 드러나 잘 되든 안 되든 티가 납니다.

부하가 전 기간에 고르게 걸립니다. W1에 F1을 내고 W3~W5 내내 튜닝합니다.

**안 맞는 사람**: 결과가 안 나오는 기간을 견디기 힘든 사람. 임베딩 튜닝은
며칠씩 진전이 없다가 갑자기 좋아지는 일이 흔합니다.

# 역할 3 — 상태 추적 · 측정

> **항목이 지금 어떤 상태인지 판정하고, 팀 전체의 숫자를 만든다.**

## 하는 일

| 주차 | |
|---|---|
| **W1** | 상태 전이 구현(**전이표가 문서에 이미 다 있습니다**). **공통 평가 러너** — 다섯 명이 이걸로 지표를 냅니다. 신호등 패널 |
| **W3** | 재발 자동 탐지 · **재발 재현율 첫 측정** · 30초 판정 기준을 데이터로 확정 |
| **W4** | 상태 정확도 튜닝 · 평가를 CI에 연결해 회귀 방지 |
| **W5** | **재발 재현율 최종 수치** ← 발표의 핵심 숫자 |

**신호등 패널과 필수 항목 패널을 소유합니다** — 화면 ②의 왼쪽 두 열.

## 필요한 것

규칙 구현 + **평가 설계**. 전이 자체는 표대로 구현하면 되지만,
**"희소한 사건을 어떻게 채점할 것인가"** 가 진짜 어려운 부분입니다.

## 어필점

> **개발** *"대화 상태 추적 및 평가 파이프라인 구축, 희소 이벤트 재현율 0.NN"*

**팀의 지표 인프라를 소유합니다.** 다섯 명의 숫자가 전부 이 평가 러너에서 나옵니다.

설명할 거리가 둘 있습니다.
**① 상태를 필드가 아니라 이벤트 로그로 둔 판단** — 재발을 5번째 상태로 두면 이력이 사라지고
드문 사건이 전체 정확도에 묻혀 측정 자체가 무의미해집니다.
**② 자동 확정의 방향성** — 재발은 자동 확정하고 체크리스트는 안 하는 이유가
"오탐이 안심시키느냐 경고하느냐"로 갈립니다.

## Q&A에서 답할 것

**Q&A에서 가장 깊은 질문이 오는 자리입니다.** 우리 차별점이 여기라서요.

- **"재발을 어떻게 잡아요?"** → 이벤트 로그 + 등급 역전. **왜 상태로 안 뒀는지**
- **"그 수치 어떻게 쟀어요?"** → **심어서 측정했다는 걸 먼저 말하고** 사건 검출 재현율로 답
- **"틀리면 어떻게 돼요?"** → 자동 확정하되 탭으로 되돌리고, 그 되돌림이 데이터로 쌓임
- **"왜 재현율이 지표예요?"** → 놓치면 제품이 존재할 이유가 없어서. 정확도도 함께 측정

## 알고 고르세요

🟡 **가장 깊이 파고드는 질문을 받습니다.** 발표는 조장이 하지만, *"그래서 그건 어떻게 했나요"*
가 나오면 이 자리로 넘어옵니다. **깊은 대화를 즐기는 사람에게 가장 좋은 자리입니다.**

구현 난이도 자체는 중간입니다. 전이표가 이미 있어 W1은 비교적 수월하고,
W3~W5의 측정·튜닝이 진짜 일입니다.

**안 맞는 사람**: 파고드는 질문을 받는 게 부담스러운 사람.

# 역할 4 — 생성

> **상태를 문장으로 바꾼다.** 카드와 리포트 — 사용자가 실제로 읽는 것 전부.

## 하는 일

| 주차 | |
|---|---|
| **W1** | 카드 후보를 규칙으로 뽑고 LLM으로 문장 한 줄. 1차 리포트(발견) 템플릿 |
| **W3** | 리포트 1차 완성 · 카드 실시간 갱신 · 첫 미팅 화면(과거 이력이 없을 때) |
| **W4** | 2차 리포트(변화) 분기 · 필수 항목 미완료 처리 |
| **W5** | 3차 리포트(패턴) · **발표 데모 시나리오 구현** |

**카드 패널과 리포트 화면을 소유합니다** — 화면 ②의 오른쪽 열과 화면 ③ 전체.

## 필요한 것

프롬프트 경계 설계 · 구조화 출력 · 문서 생성. **가장 "AI 애플리케이션"스러운 자리.**

## 어필점

> **개발** *"구조화 출력 기반 LLM 앱 설계, 근거 인용률 100% · 할루시네이션 0"*
> **기획** *"차수별 리포트 3종 설계 — 사용자가 무엇을 읽어야 하는가"*

**LLM을 어디까지 믿을 것인가에 선을 긋는 자리입니다.** 후보는 규칙으로 뽑고 LLM은
마지막 한 줄만 씁니다. *"저희는 LLM에게 판단을 안 맡겼습니다"* 는 현직자가 좋아하는 답입니다.

리포트의 모든 서술에 근거 발화를 붙여 **환각을 설계로 0**으로 만듭니다.
"프롬프트를 잘 썼다"가 아니라 "구조로 보장했다"는 게 차이입니다.

**발표에서 화면에 뜨는 건 대부분 이 역할의 산출물입니다.**

## Q&A에서 답할 것

- **"LLM 어디에 쓰셨어요?"** → **"판단은 안 맡겼습니다."** 무엇을 다룰지는 상태가 정하고 LLM은 문장만
- **"환각 없나요?"** → 근거 인용률 100%를 **구조로 보장**. 근거 없는 문장은 아예 못 나옴
- **"첫 미팅에는 보여줄 게 없지 않나요?"** → 가상의 과거 이력을 만들지 않고 기본 체크로 대체한 이유
- **"리포트가 차수마다 다른가요?"** → 1차 발견 / 2차 변화 / 3차+ 패턴. **왜 갈랐는지**

## 알고 고르세요

🟡 **앞단에 의존합니다.** 상태가 나와야 카드를 만들 수 있어 W1~W3에는 fixture로 작업합니다.
반대로 **W4~W5에 부하가 몰립니다** — 리포트 3종과 데모 시나리오가 겹칩니다.

발표 데모가 깨지면 가장 눈에 띄는 자리이기도 합니다.

**안 맞는 사람**: 남의 출력이 확정되기 전에 작업하는 게 답답한 사람.

# 역할 5 — 템플릿 · 누적 ✅ 조장

> **무엇을 추적할지 정하고, 미팅을 차수로 잇는다.** 계약의 중심.

## 하는 일

| 주차 | |
|---|---|
| **W1** | **반대사유 30개 + 필수 항목 12개 이하, 예문 약 480문장** ← 이번 주 최대 작업. 스키마 로더·검증 규칙. 딜 목록 행 컴포넌트. 미팅 전 브리핑 화면 |
| **W3** | 이월 규칙 엔진 · 미팅↔딜 연결 · 사후 연결 |
| **W4** | 프리로드 규칙(1차 미해결 무조건 이월) · 잘못 이은 딜 끊기 |
| **W5** | 템플릿 커버리지 수치 · 저작 도구 마감 · **스펙 변경 로그 회고 정리** |

> **예문 480문장의 내역** — 항목 표현 `aliases` 210문장(42항목 × 5)에 더해,
> 1층 슬롯마다 충족 신호 `cues` 3개와 차단 신호 `blockers` 3개가 붙습니다.
> 슬롯을 항목당 1.5개로 잡으면 약 270문장이 추가됩니다.
> **차단 신호가 곧 재발 탐지의 입력**이라 여기서 타협하면 역할 2·3의 지표가 같이 내려갑니다.

여기에 더해 **스펙 동결권**을 가집니다 — `2`(데이터 모델) `3`(API) `5`(폴더·스택)를
바꾸려면 조장을 거칩니다. 변경 요청은 `guidelines/0`의 4단계를 따르고,
**조장이 변경 로그를 남깁니다** — W5 회고의 재료가 됩니다.

## 🔴 여러분 일과 어떻게 물리나

**역할 5가 항목 풀을 못 내면 역할 2가 착수를 못 하고, 라벨링도 시작이 안 됩니다.**

```
   [5] 무엇을 추적할지 정한다
        │
   [1] 소리 → 발화   →   [2] 어느 항목인가   →   [3] 어떤 상태인가   →   [4] 뭐라고 말할까
                                                         │
                                                    [5] 차수를 잇는다
```

**그래서 조장이 W1 첫 이틀 안에 잠정 항목 풀을 먼저 냅니다.**

라벨된 역할극 fixture — 정답이 붙은 대화 데이터 — 는 **항목 ID를 기준으로** 붙습니다.
그래서 fixture가 먼저 나올 수는 없고, 순서가 이렇게 됩니다.

```
W1 화요일   잠정 항목 풀 (항목 ID 동결)   ← 조장
    ↓
W1 수~목    fixture 라벨링                ← 전원
    ↓
W1 목~금    각자 자기 함수를 채점하며 개발  ← 앞단 없이 가능
```

**동결되는 건 항목 ID뿐입니다.** 표시 이름과 예문은 W3까지 계속 보강합니다 —
ID만 고정돼 있으면 라벨링한 fixture가 나중에 무효가 되지 않습니다.

**이 순서가 지켜지면 아무도 남을 기다리지 않습니다.** fixture만 있으면
역할 2·3·4는 앞단 구현이 없어도 첫 슬라이스를 만들고 지표를 낼 수 있습니다.

## 역할 5가 정한 것 중 여러분이 지켜야 할 것

| 규칙 | 왜 |
|---|---|
| **항목은 만들지 않고 고른다** | 자유 생성하면 같은 얘기가 다른 항목으로 불어나 **채점이 불가능**해집니다 |
| **목록에 없는 말은 `기타` 한 칸에 원문 그대로** | 억지로 가까운 항목에 붙이면 지표가 오염됩니다 |
| **항목 ID는 템플릿을 넘어 고정** | 이게 있어야 1차 항목이 2차로 이월됩니다 |

## 어필점

**이 자리의 특징은 같은 일을 두 가지로 쓸 수 있다는 것입니다.**

> **기획** *"영업 도메인 분석 및 항목 체계 설계, 제품 스펙 동결·변경 관리"*
> **개발** *"YAML 기반 도메인 스키마와 검증 파이프라인 설계, 차수 간 상태 이월 엔진 구현"*

역할 4도 양쪽으로 읽히지만 결이 다릅니다. **역할 4의 기획은 화면 쪽**입니다 —
사용자가 무엇을 읽을지. **역할 5의 기획은 제품 쪽**입니다 — 무엇을 추적할지 정하고,
범위를 긋고, 스펙 변경을 통제합니다. 기획 직무 면접에서 실제로 파고드는 건 뒤쪽입니다.

**제품의 해자를 만드는 자리입니다.** 차수별 누적이 차별점 둘 중 하나인데,
그걸 지탱하는 게 이월 규칙과 전역 항목 ID입니다.

그리고 **스펙 동결권은 작업이 아니라 책임**입니다. 다섯 명이 병렬로 짜는 동안
데이터 모델과 API가 흔들리지 않게 잡는 자리라, "무엇을 안 바꿨는지"까지 말할 수 있습니다.

## Q&A에서 답할 것

- **"항목을 왜 AI가 안 만들죠?"** → 자유 생성하면 채점 기준이 사라집니다. **설계 원칙**
- **"차수를 어떻게 이어붙여요?"** → 딜 단위 + 전역 항목 ID. **자동 매칭을 왜 안 썼는지**
- **"템플릿은 누가 만드나요?"** → 지금은 우리가. 확장기에는 사용자가 직접 등록하는 구조로
- **"항목이 40개면 화면이 복잡하지 않나요?"** → 프리로드로 켜는 것만. 상한과 정렬 규칙

# 이 프로젝트를 포트폴리오로 어떻게 쓰나

역할을 고르기 전에 알아둘 게 하나 더 있습니다. **어떤 자리를 맡든, 남는 건 같은 형태입니다.**

## 시장이 실제로 보는 것

AI 프로덕트 채용을 분석한 자료들이 공통으로 말하는 게 있습니다 —
**"무엇을 만들었나"보다 "무엇을 만들기로 판단했나"를 본다**는 것입니다.

| 강한 신호 | 약한 신호 |
|---|---|
| 어떤 문제를 고르고 왜 그게 중요한지 판단한 근거 | **기능 나열 · 릴리스 속도** |
| **데모는 잘 되는데 운영에서 깨지는 걸 접어본 경험** | 자격증 |
| 모델 평가를 설계하고 수치로 말하는 능력 | "열심히 했습니다" |
| 파운데이션 모델로 실제로 뭔가를 출시해본 경험 | 결과만 있고 과정이 없는 것 |

**릴리스 속도를 앞세우면 오히려 감점**이라는 게 반복해서 나옵니다.
"기능을 많이 냈다"는 실행자 서사이고, 채용은 판단하는 사람을 찾고 있어서입니다.

## 그래서 각자 W5에 세 가지를 남깁니다

**① 내 지표 Before → After**
> *"매칭 F1이 0.61에서 시작했는데, 표현 사전을 라벨링 결과로 키워서 0.78이 됐습니다"*

**② 내가 안 만들기로 한 것 하나와 그 이유**
> *"목록에 없는 발화를 가까운 항목에 억지로 붙이는 로직을 넣을 수 있었지만 안 넣었습니다.
> 매칭 수치는 올라가지만 그 수치가 거짓이 되기 때문입니다."*

**③ 틀렸던 판단 하나와 무엇을 바꿨는지**
> *"30초 쿨다운을 감으로 정했는데 fixture를 돌려보니 재발을 놓치고 있었습니다.
> 곡선을 그려서 다시 잡았습니다."*

**③번을 숨기지 마세요.** 실패를 정직한 수치로 말하는 게 신입 포트폴리오에서 가장 강한 장면입니다.
숨긴 사람은 면접에서 한 번 더 물어보면 무너집니다.

## 프로젝트 하나를 서술하는 형식

신입 합격 포트폴리오는 대체로 이 다섯 단계를 반복합니다. 역할이 뭐든 그대로 채워집니다.

| | | 예시 (역할 3) |
|---|---|---|
| **WHY** | 왜 이 문제인가 | 회의록은 말한 걸 남기지만 *안 끝난 것*은 아무도 안 들고 있다 |
| **HOW** | 어떻게 검증했나 | 상태를 필드가 아니라 이벤트 로그로 두면 재발이 사건으로 측정된다 |
| **WHAT** | 무엇을 설계·구현했나 | 전이 규칙 + 등급 역전 판정 + 공통 평가 러너 |
| **RESULT** | 수치 | 재발 재현율 0.NN / 상태 정확도 0.NN |
| **LEARN** | 배운 것 · 다음 | 희소 사건은 전체 정확도에 묻힌다. 사건 단위로 재야 한다 |

**RESULT 칸을 채우려고 지표를 하나씩 나눈 것입니다.** 다섯 명이 각자 자기 숫자를 갖고 있으면,
포트폴리오에서 서로 겹치지 않습니다.
