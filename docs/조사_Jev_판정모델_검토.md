# Jev(TypeSafe AI) 판정 모델 검토 — 2026-09-22

조사 이종훈

**Jev는 지금 쓰는 `gpt-5.6-luna`의 대체가 아니라 분업 상대입니다.** 우리 판정은 ①어느 칸이 찼는지 판단과 ②마스코트 대사·이야기 문장 생성을 한 번에 하는데, Jev는 **①만 할 수 있고 ②는 문서가 직접 「못 한다」고 적어 뒀습니다.** 그래서 검토의 질문은 *"바꿀까"*가 아니라 ***"①을 떼어 줄 만한가"***이고, 그 답을 가르는 것은 **한국어 성능**과 **확신도가 쓸 만한 숫자인지**입니다. 둘 다 아직 재지 않았습니다.

---

## 이 검토의 범위

**읽은 것** — 제품 홈페이지, 공식 문서의 색인·`confidence`·`Jev 1.13 jaggedness`(한계) 문서, 독립 리뷰 2건, 검색 결과 요약.

**읽지 않은 것** — API 참조 문서, 가격 페이지, SDK, 콘솔. **그리고 한 번도 돌려보지 않았습니다.**

**따라서 이것은 성능 검토가 아니라 「무엇을 재면 정해지는가」의 정리입니다.**

- 문서와 리뷰는 **2026-09-22에 열람**했습니다. 열람일이며 효력일이나 최신성을 보증하는 날짜가 아닙니다
- 속도·값·정확도 수치는 **벤더 또는 리뷰어의 주장**이고 **독립적으로 재현하지 않았습니다**
- 한국어 성능에 대한 언급은 **읽은 범위 어디에도 없었습니다** — 없다고 확정한 것이 아니라 확인되지 않았다는 뜻입니다

아래 다섯 절은 각각 **확인된 것 · 조건부 함의 · 확인되지 않은 것**으로 나눠 적었습니다. 세 번째 칸이 비어 있다는 것은 **제품에 그것이 없다는 뜻이 아니라 이 조사로는 알 수 없다는 뜻**입니다.

## 1. 기능은 원시 기능 셋이다 — Choice · Score · Noul

### 확인된 것

홈페이지가 내세우는 문구(*"Decisions, not strings"* · *"Calibrated confidence"* · *"Zero Hallucinations"*)는 **기능 목록이 아니라 주장**입니다. 실제로 부를 수 있는 것은 문서의 **원시 기능(primitives) 셋**입니다.

| | 하는 일 | 돌려주는 것 |
|---|---|---|
| **Choice** | 목록에서 하나 고르기 | `choice` · `probabilities` · `confidence` |
| **Score** | 기준표로 점수 매기기 | `score` · `probabilities` · `confidence` |
| **Noul** | *"이 말이 참인가"* | 0~1 값 |

설계 철학은 **「원자적 질문을 코드로 조합한다」**입니다. 복잡한 판단을 한 번에 묻지 않고 작은 질문 여러 개로 쪼개 병렬로 물은 뒤 **조합은 애플리케이션 코드가 합니다.** 문서는 *"질문을 더해도 응답 시간이 거의 안 변한다"*고 적었습니다.

확신도는 **확률 분포의 모양**에서 나옵니다 — 세 선택지면 `(3 × 가장 큰 확률 − 1) / 2`. 분포가 한쪽에 몰리면 높고 퍼지면 낮습니다.

### 조건부 함의

**이 철학이 우리 규칙 4와 글자 그대로 같습니다** — *"수준은 규칙이 계산한다. LLM은 신호만 표시한다."* 우리가 설계로 정해 둔 것을 이 모델은 **구조로 강제**합니다. 맞다면 규칙 4를 어길 방법이 없어지는 셈입니다.

문서가 권하는 문턱은 **0.9 이상 자동 처리 · 0.5~0.9 확인 · 0.5 미만 사람에게**이고, *"경계를 어디 두느냐는 위험도에 달렸다"*고 덧붙입니다.

### 확인되지 않은 것

한 번에 보낼 수 있는 질문 수, 상태 크기 한계, 맥락 창 길이, 속도 보장, 요율 제한. **확신도 0.8이 실제로 80%를 뜻하는지**(보정의 실측) 역시 문서가 명시하지 않았습니다 — *"보수적으로 시작해 자기 데이터로 시험하고 조정하라"*고만 합니다.

### 같이 생각해 볼 질문

- 우리 판정 16필드를 **원자적 질문 몇 개로 쪼갤 수 있을까요?** 쪼개면 코드가 무엇을 조합해야 하나요?
- 확신도 문턱을 우리 제품에 두면 **0.5 미만일 때 「사람에게」가 무엇을 뜻하나요?** 아이는 기다리고 있는데요.
- 지금 규칙이 어림으로 세는 것 중, **확신도가 있으면 근거를 갖게 되는 것**은 어느 판단인가요?

## 2. 루나와의 관계는 대체가 아니라 분업이다

### 확인된 것

| | `gpt-5.6-luna` (지금) | **Jev** |
|---|---|---|
| 하는 일 | 판단 + **글 생성** | **결정만.** 글은 못 만듦 |
| 속도 | p95 **2.4초** (우리 측정) | **70~500ms**, 보통 100ms (리뷰어 주장) |
| 값 | **권당 21.6원** (우리 측정) | 100만 입력 토큰당 **$0.042** · 출력 무료 |
| 정확도 | slot_1 80% (우리 평가셋) | 자체 4워크플로 벤치 **68%** |
| 확신도 | 없음 | **있음** |

한계 문서 9번 항목이 **`Generation` — *"글을 만들도록 학습되지 않았다. 억지로 시키면 느리고 잘 안 된다"***입니다. 독립 리뷰도 같은 결론입니다 — *"분류·점수·라우팅에는 정말 좋지만 쓰거나 추론하는 LLM의 대체가 아니다."*

### 조건부 함의

**우리 판정은 한 번에 두 일을 합니다.** ①아이 말이 어느 칸인지·다음에 뭘 물을지 판단 ②마스코트 대사(받아주기·되돌려주기·질문)와 이야기 문장 생성. **Jev가 가져갈 수 있는 것은 ①뿐이고 ②는 루나가 그대로 남습니다.**

그러면 `CLAUDE.md`의 *"판정 + 생성 = 한 모델, effort 두 설정"*이 **두 모델로 쪼개집니다.** 호출이 하나에서 둘로 늘고, 대신 ①이 2.4초에서 0.1초대로 내려갑니다.

**속도가 매력적인 이유는 값이 아니라 리액션입니다.** 지금 덮어야 하는 구멍이 **판정 2.40 + TTS 첫 소리 1.32 = 3.72초**인데, 판정이 0.1초가 되면 구멍이 **1.4초대**로 줄어 **리액션 한 마디로 덮입니다.**

⚠️ **68%를 우리 80%와 나란히 놓으면 안 됩니다.** 다른 과업·다른 평가셋·다른 표본입니다. 이 숫자가 말해 주는 것은 *"중급 LLM 정도의 난이도를 다룬다"*이지 *"우리 슬롯 판정에서 68%가 나온다"*가 아닙니다.

### 확인되지 않은 것

우리 평가셋에서의 실제 정확도, 한국어 성능, 두 모델로 쪼갰을 때의 실제 총 지연(호출 두 번의 합), 그리고 **생성을 루나에 남길 때 판정 결과를 프롬프트로 넘기는 비용**.

### 같이 생각해 볼 질문

- 판정과 생성을 쪼개면 **마스코트 대사가 판정 결과를 기다려야** 하나요, 아니면 동시에 갈 수 있나요?
- 구멍이 1.4초로 줄면 **리액션을 아예 안 써도 되는** 지점이 오나요? 그 경계는 몇 초인가요?
- 지금 판정이 **문제가 아닌데**(JSON 100%) 바꾸는 이유가 속도뿐이라면, 그 속도가 아이 경험에서 실제로 무엇을 바꾸나요?

## 3. 우리 서비스에서 쓸 자리 셋

### 확인된 것

원시 기능 셋을 우리 흐름에 대 보면 자리가 셋 나옵니다.

| 자리 | 쓸 기능 | 지금 |
|---|---|---|
| **슬롯 판정** — *"이 말은 12칸 중 어디냐"* | `Choice` | 루나. JSON 100% · 2.4초 |
| **수준 신호** — *"까닭을 말했나" · "덧붙였나"* | `Noul` | 루나가 있다/없다만 표시 |
| **안전 필터** — *"이 말이 그림책 한 쪽에 들어가도 되는가"* | `Noul` | 규칙 금칙어 + LLM 필터 |

세 번째가 특히 맞는데, **규칙 7의 판단 기준 한 줄이 그대로 Noul 질문 문장**입니다. 그리고 리뷰가 꼽은 적합 용도에 *"안전 검사(safety checks)"*가 들어 있습니다.

### 조건부 함의

**확신도가 채우는 빈 자리가 하나 분명히 있습니다.** `README`에 *"확신 없으면 버린다"*고 적혀 있는데 **지금은 버릴 기준 자체가 없습니다.** 규칙 9도 *"LLM이 만든 문장에 금지어가 하나라도 있으면 그 답을 버리고 미리 만든 문장을 쓴다"*인데, 이건 금지어 목록에 걸릴 때만 작동하고 **애매한 경우를 못 잡습니다.**

규칙 7이 *"놓치는 것보다 과차단이 위험하다"*이므로, **문턱을 낮게 두고 애매한 것은 통과시키는** 방향이 우리 원칙과 맞습니다.

### 확인되지 않은 것

한국어 아이 발화에서 `Noul`이 *"까닭을 말했나"*를 실제로 가리는지, 확신도가 우리 평가셋에서 보정되어 있는지, 그리고 **과차단률** — 규칙 7이 가장 경계하는 숫자인데 아직 재는 방법도 정하지 않았습니다.

### 같이 생각해 볼 질문

- 안전 필터를 Noul로 바꾸면 **과차단을 무엇으로 재나요?** *무섭다·괴물·싸웠다*가 통과하는지 보는 케이스가 평가셋에 있나요?
- 확신도 낮음이 **아이 화면에서는 무엇으로 보이나요?** 되묻기인가요, 그냥 넘어가는 것인가요?
- 세 자리 중 **하나만 먼저 바꿔 본다면** 어디가 가장 안전한가요?

## 4. 오브젝트 배치 — 절반만 되고, 필요한 절반이 아니다

### 확인된 것

**Jev는 텍스트 전용입니다.** 문서에 이미지·오디오 입력 언급이 없고, 리뷰가 부적합 용도로 *"이미지 분류(텍스트 전처리 없이는)"*를 명시합니다.

배치는 두 판단으로 갈립니다.

| | Jev로 되나 | 왜 |
|---|---|---|
| **무엇을 얹을까** — *"공룡나라"* → 바위·나무·별 | **됩니다** (`Choice`) | 텍스트 판단입니다 |
| **어디에 얹을까** — 지평선 아래 빈 칸 | **안 됩니다** | 그림을 봐야 합니다 |

### 조건부 함의

**「어디에」는 이미 풀려 있습니다.** 09-22에 배경을 읽어 지평선과 빈 칸을 찾는 계산을 붙였고, **GPU를 안 쓰고 수십 ms**입니다(`assets/tools/place_props.py`). 그림 한 장이 2.4초인 것에 비하면 공짜라 **바꿀 이유가 없는 자리**입니다.

**「무엇을」은 지금 프리셋 목록에서 고정으로 얹습니다.** 아이 말에 따라 고르게 하려면 Choice가 맞긴 한데, 이건 **지금 문제로 올라온 적이 없는 항목**입니다.

### 확인되지 않은 것

아이 말에서 소품을 고르는 판단이 **실제로 필요한지** — 지금 프리셋 고정으로도 이야기가 성립하는지 세션을 돌려 본 기록이 없습니다.

### 같이 생각해 볼 질문

- 아이가 *"우주선도 있어!"*라고 했을 때 **프리셋에 없으면 어떻게 하는 게 맞나요?** 빼나요, 비슷한 걸 얹나요, 만드나요?
- 소품을 아이 말에 맞춰 고르면 **「또 이거네」가 줄어드나요?** 그걸 무엇으로 재나요?

## 5. 문서가 직접 적어 둔 한계 아홉

### 확인된 것

`Jev 1.13 jaggedness` 문서가 실패 유형 아홉을 스스로 적어 뒀습니다. **우리에게 걸리는 것은 다섯입니다.**

| 한계 | 우리에게 |
|---|---|
| **세기를 못 한다** — *"계산기가 아니다"* | 우리 핵심 지표가 「주고받기 횟수」인데 **그건 코드가 셉니다.** 안 걸립니다 |
| **날짜를 텍스트로 읽는다** | 부모 리포트의 *"9/10 · 9/14 · 9/17"* 비교를 **맡기면 안 됩니다** |
| **쓸데없는 맥락이 많으면 정확도가 떨어진다** | 판정에 **슬롯 상태 전체를 넣는 지금 방식이 불리**할 수 있습니다. 문서는 *"걸러서 보내라"*고 권합니다 |
| ⚠️ **주입에 흔들린다** — *"상태를 적대적으로 다루지 않는다"* | **아이 말이 그대로 들어가는 자리**입니다 |
| **구조적 불변식이 없다** — `P(참) + P(거짓) = 1`을 보장하지 않는다 | 규칙이 확신도로 계산할 때 **합이 1이라고 가정하면 안 됩니다** |

그리고 점수에 대한 경고 하나 — ***"1.4가 「40% 지점」을 뜻하지 않는다."*** 점수 사이를 내삽해 읽지 말라는 뜻입니다.

### 조건부 함의

**「주입에 흔들린다」가 우리에게 가장 무겁습니다.** 아이 말은 적대적이지 않지만, **부모 협업 모드에서는 부모가 질문을 직접 넣습니다.** 그 입력이 판정 상태에 들어가면 경로가 열립니다. 규칙 6이 실명을 폰에서 가리게 해 놨지만 **주입은 실명 문제와 다른 축**입니다.

**「맥락이 많으면 떨어진다」는 우리 프롬프트 설계를 바꿉니다.** 지금은 모델이 슬롯 상태 전체를 읽고 다음 질문을 정하는데(`backend/app/routers/judge.py` 주석), Jev로 옮기면 **무엇을 걸러 보낼지**를 우리가 정해야 합니다.

### 확인되지 않은 것

**한국어 성능.** 읽은 범위에 언급이 전혀 없습니다. 어제 같은 한국어 프롬프트가 모델에 따라 **토큰 6,129 대 3,987**로 갈린 것을 봤으므로, 한국어 처리가 모델마다 크게 다르다는 것은 우리가 이미 겪었습니다. **68%가 한국어에서 나올지는 재봐야 압니다.**

### 같이 생각해 볼 질문

- 부모가 넣은 질문이 판정 상태에 들어갈 때, **주입을 막는 자리는 어디여야 하나요?** 백엔드인가요 폰인가요?
- 상태를 걸러 보내야 한다면 **무엇을 빼도 판정이 성립하나요?** 지금 16필드 중 몇 개가 실제로 필요한가요?
- 한국어에서 안 된다는 결과가 나오면, **그 결과를 어떻게 알아보나요?** 무엇을 보면 「안 된다」고 말할 수 있나요?

## 그래서 다음에 할 것 — 의존성 순

**앞의 것이 뒤의 것을 쉽게 만드는 순서로 적었습니다.** 첫 항목이 나오면 나머지 판단이 훨씬 적은 가정 위에서 굴러갑니다.

1. **한국어 100문항을 `Choice`로 돌린다**
   `eval/` 하네스에 어댑터 하나를 붙인다. 09-21에 Anthropic 어댑터를 만들어 봤으므로 같은 모양이다. **이 하나가 「한국어에서 되나」와 「우리 평가셋에서 몇 점인가」를 같이 답한다.**
2. **확신도가 보정되어 있는지 본다**
   1번의 응답에서 확신도별 실제 정답률을 묶어 본다. **0.9 구간이 실제로 90%에 가까운지**가 이 기능을 쓸 수 있는지의 전부다.
3. **판정 16필드를 원자적 질문으로 쪼개 본다**
   Choice 몇 개 · Noul 몇 개로 나뉘는지, 조합을 코드가 할 수 있는지. **쪼갤 수 없는 필드가 있으면 그게 루나에 남는다.**
4. **상태를 얼마나 걸러야 하는지 본다**
   전체를 넣은 것과 걸러 넣은 것의 정확도를 비교한다. 문서의 경고가 우리 크기에서도 유효한지.
5. **속도를 우리 위치에서 잰다**
   70~500ms는 미국 서부 기준이라고 리뷰어가 경고했다. **한국에서 재야 리액션 설계에 쓸 수 있다.**

**1번만 해도 「쓸까 말까」가 갈립니다.** 2~5번은 1번이 통과했을 때의 일입니다.
