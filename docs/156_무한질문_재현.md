# #156 동화 종료 판정 재현 (10-06)

## 확인한 범위

- S7 개발 앱 `b004fe7`의 12:44~12:50 KST 로그: 판정 15개 모두 미완료, 해결 칸이 채워진 뒤에도 6차례 질문. 실제 발화는 로컬에만 보관한다.
- 앱 없이 공개 `/judge`에 익명 재료를 보냈다. 결말 답·새 행동·「더 없어」 각각 2회가 모두 `reason=jev / story_ready=false / next_slot=null`이었다. extra 제거·template C·template 없음도 각 1회 같은 상태였다.
- 이어 같은 익명 재료를 `/turn`으로 재생하니 **6회 중 5회 완료, 1회 미완료·다음 칸 없음**이었다(전체 응답 중앙값 2.587초). 모델 응답 또는 운영 상태에 따라 달라지는 결과다. 앞의 9/9를 모든 실행의 실패율로 해석하지 않는다. 두 경로를 동시에 통제해 비교한 모델 품질 실험도 아니다.
- 이 재현에는 Android 패키지·마이크·기기 저장소가 없다. `kr.clap.otto`와 `.dev`가 나뉜 사실만으로 이 서버 응답을 설명할 수 없다.

## 수정한 경로와 한계

Jev는 칸 선택을 비울 수 있다. `judge.run()`은 이전에 Jev 통신 오류에서만 기존 전체 판정으로 돌아갔으므로, 미완료인데 다음 칸도 없는 성공 응답이 대사 모델에 도달했다. 대사 모델은 후속 질문을 만들고, 앱은 그 질문을 다시 물었다.

동화에서 서버 규칙 적용 뒤 **미완료·다음 칸 없음**이면 원래 요청을 기존 전체 판정에 한 번 넘긴다. 완료를 강제로 참으로 바꾸지 않는다. 정상 Jev 판정·다른 모드는 기존 경로다. 모델·프롬프트·문턱은 바꾸지 않는다. 이 복구는 판정 호출 1회를 추가하므로 실제 지연과 비용은 #172에서 따로 본다.

공개 응답에는 Jev의 원래 확신도나 버린 선택이 없으므로 「반드시 0.6 아래여서 생겼다」고 확정하지 않는다. 자동 검사는 제어한 모델 응답으로 복구·질문 제거 경로를 검증한 것이다. 전체 판정의 실제 품질과 S7 완주를 보장하는 측정은 아니다.

## 배포 전후 같은 입력으로 확인

`eval/fixtures_story_ending_loop.jsonl`은 이름·실제 발화가 없는 합성 재료다. `replay_story_ending_loop.py`는 키·`.env`를 읽지 않고 지정한 서버의 `/turn`을 호출한다. `/health`가 정상이며 mock=false일 때만 진행한다.

```powershell
python eval/replay_story_ending_loop.py --url https://otto-back.shelldocs.cloud --runs 2 --output "$env:TEMP/otto-ending-result.json"
```

- 종료 코드 0: 이 합성 입력이 모두 완료 판정이고 추가 질문 없음
- 1: 완료 재현 중 실패가 남음
- 2: 연결·설정 오류(품질 통과로 해석하지 않음)
- `stranded`: 완료도 다음 칸도 없는 판정 개수
- 응답·지연이 output 파일에 남는다. 이 파일은 커밋하지 않는다.
- 배포 전 PR 코드를 쓰는 설정된 서버에서도 같은 명령의 `--url`만 실제 주소로 바꿔 실행한다. 서버 주소나 키를 추측하지 않는다.

합성 검사가 통과해도 S7에서 자연스러운 이야기 2~3판을 선물 화면까지 완료하고 #172 호출 수와 대조한다. #156은 그 확인 전에 닫지 않는다.
