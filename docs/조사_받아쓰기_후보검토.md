# 받아쓰기 후보 검토 — Grok Voice Transcribe 2.0 (2026-09-22)

조사 이종훈

**후보로 올릴 만하다. 다만 이유가 「정확도가 좋아서」가 아니다.** 이 모델이 우리 병목을 정면으로 겨냥하는 기능을 하나 갖고 있다 — **핵심 낱말 편향(key term biasing, 요청당 100개)**. 우리 받아쓰기 문제는 전체 정확도가 아니라 **프리셋 매칭 65%**(합격선 95%)이고, 프리셋은 *공룡나라·뿌뿌·쿵쿵이* 같은 **미리 아는 낱말 목록**이다. 그걸 편향어로 넣는 것이 이 기능이다. **그리고 같은 이유로, 자체 `faster-whisper`에도 같은 편향을 걸고 비교해야 공정하다** — 안 그러면 기능 차이를 모델 차이로 읽게 된다.

---

## 이 검토의 범위

**읽은 것** — 제품 발표 페이지, `docs.x.ai` 음성 가이드, 검색으로 확인한 API 보존 정책과 소비자 약관 요약.

**읽지 않은 것** — **개인정보 정책 원문**(HTTP 403으로 막혔다) · 엔터프라이즈 약관 원문 · API 참조. **그리고 한 번도 돌려보지 않았다.**

**아동 음성으로는 아무도 재지 않았다** — 우리도, 벤더도. 발표 페이지의 수치는 **성인 다국어 짧은 구문**이다.

**따라서 이것은 「쓸 수 있나」의 답이 아니라 「무엇을 재면 정해지는가」다.**

## 1. 무엇인가

### 확인된 것

| | |
|---|---|
| 모델 | `grok-voice-transcribe-2.0` |
| 엔드포인트 | `POST https://api.x.ai/v1/stt` (멀티파트) · 스트리밍은 **WebSocket** |
| 언어 | **25개 · 한국어 포함** (written-form formatting 대상에 명시) |
| 값 | **배치 $0.10/시간 · 스트리밍 $0.20/시간** |
| 같이 오는 것 | **핵심 낱말 편향(100개/요청)** · 단어별 타임스탬프와 **확신도** · **화자 분리** · 다채널(8) · 필러 제거 · 턴 감지 — **전부 추가 요금 없음** |
| 정확도 주장 | 1.0 대비 2배 · Artificial Analysis 스트리밍 32개 중 1위 · **짧은 구문 WER 20.6% → 6.8%** |

### 조건부 함의

**우리 값으로 환산하면 작다.** 한 세션이 15분이지만 **VAD가 말소리 구간만 보내므로** 실제 오디오는 3~5분쯤이다. 배치 $0.10/시간이면 **권당 7~11원**이다. 판정이 권당 21.6원이니 같은 자릿수다.

**화자 분리가 공짜로 딸려 온다.** 지금 설계에서 빠진 기능이지만, 나중에 되살릴 때 **따로 올릴 필요가 없어진다** — 우리 GPU에서 783 MiB를 쓰던 그 자리다.

### 확인되지 않은 것

- **지연.** 발표 페이지에 수치가 없다. 스트리밍이 WebSocket인데 **한국에서 얼마인지 모른다**
- 오디오 길이 상한 · 요청 크기 상한
- **확신도가 보정되어 있는지** — Jev에서 그랬듯 벤더 주장과 실측은 다르다

### 같이 생각해 볼 질문

- 배치와 스트리밍 중 어느 쪽인가요? 값이 두 배 차이인데 **아이가 한 문장 말하고 끊는** 우리 흐름에서 스트리밍이 필요한가요?
- 화자 분리가 공짜로 오면 **설계에서 뺀 판단이 바뀌나요?** 빠진 이유가 「비용」이 아니라 「필요 없어서」였는지 다시 봐야 합니다

## 2. 왜 후보인가 — 우리 병목과 맞물린다

### 확인된 것

지금 막고 있는 것은 **정확도 전반이 아니다.**

| 잰 값 | 합격선 | |
|---|---|---|
| 폰 온디바이스 **프리셋 매칭 65%** | ≥ 95% | **미달** (09-19) |
| 아이 발화 핵심 키워드 보존율 | ≥ 90% | **아직 못 잼** |

그리고 `results.md` 09-19가 이렇게 적었다 — *"프리셋 밖 발화는 맞출 목록이 없어 자모 매칭이 못 구한다"*, *"프리셋 이름 선정 — 인식률이 이름마다 크게 다르다."*

**「미리 아는 낱말 목록이 있고, 그 목록을 못 맞춘다」가 정확히 핵심 낱말 편향이 푸는 문제다.**

### 조건부 함의

**그런데 이게 이 모델만의 기능이 아니다.** `faster-whisper`에도 `initial_prompt`로 낱말을 밀어 넣는 방법이 있다. **지금까지 우리가 그걸 안 썼을 뿐이다.**

→ **비교를 이렇게 짜야 한다.**

| | 편향 없이 | **편향 걸고** |
|---|---|---|
| 자체 `faster-whisper` | 기준선 | `initial_prompt` |
| **Grok Voice Transcribe 2.0** | — | 핵심 낱말 100개 |

⚠️ **편향 없는 whisper와 편향 건 Grok을 비교하면 기능 차이를 모델 차이로 읽게 된다.** 09-20에 *"같은 프롬프트로 비교해야 유효하다"*고 정한 것과 같은 이유다.

**그리고 GPU가 비는 것이 따로 이득이다.** 09-22 측정에서 **그림과 겹쳐 돌리면 받아쓰기가 0.71 → 2.54초(3.6배)** 느려졌고, 그래서 *"아이가 말하는 동안에는 그림을 만들지 않는다"*는 제약이 생겼다. **받아쓰기를 밖으로 빼면 그 제약이 사라지고 GPU가 그림 전용이 된다.**

### 확인되지 않은 것

**아동 음성 정확도.** 발표 수치는 성인 다국어 짧은 구문이다. `guidelines/6` §6-3의 전례가 **성인 7.8% vs 아동 120.8%**인데, 그 전례가 말하는 것은 *"성인 수치로 아동을 예측할 수 없다"*이다. **이 모델에도 똑같이 적용된다.**

### 같이 생각해 볼 질문

- 프리셋 낱말이 지금 몇 개인가요? 100개 안에 들어가나요?
- 편향어에 **아이 이름**을 넣어야 하나요? 넣으면 실명이 요청에 실립니다 — 3절과 이어집니다

## 3. ⚠️ 밖으로 보내면 순서가 뒤집힌다

### 확인된 것

지금 흐름은 이렇다.

```
② 음성 → 글자      ← 여기가 밖으로 나가면
③ 이름 가리기       ← 이것보다 앞선다
```

**즉 외부 받아쓰기는 「가려지기 전 실명이 실린 음성」을 보낸다.** 판정·낭독으로 나가는 글자는 이미 `{친구1}`로 바뀐 뒤인데, **음성은 원본이다.**

### 조건부 함의

**이건 벤더 선택 문제가 아니라 순서 문제다.** Grok이든 OpenAI든 자체 GPU가 아니면 같다. 그래서 선택지가 셋이다.

| | 무엇 | 걸리는 것 |
|---|---|---|
| **A** | **자체 인프라로 남긴다** | GPU 경합이 남는다(3.6배) |
| **B** | 밖으로 보내되 **음성에 실명이 들어가는 것을 받아들인다** | 규칙 6의 *"실명은 폰을 안 떠난다"*가 깨진다 |
| **C** | **음성에서 이름을 먼저 가린다** | 음성에서 이름을 가리려면 **먼저 받아써야 한다.** 순환이다 |

→ **C는 성립하지 않는다.** 실질 선택은 A와 B이고, **B를 고르면 규칙 6을 고쳐야 한다** — 몰래 어기는 것이 아니라 바꾸는 것으로.

### 확인되지 않은 것

**아이가 실제로 실명을 얼마나 말하는지.** *"지호가"*, *"엄마가"*, *"선생님이"* — 이름을 부르는 빈도를 센 적이 없다. **적으면 B의 무게가 가벼워진다.**

### 같이 생각해 볼 질문

- 규칙 6이 지키려는 것이 **실명 자체**인가요, **실명과 아이의 연결**인가요? 후자라면 음성만으로는 연결이 안 될 수도 있습니다
- A를 고르면 GPU 경합이 남는데, **시간을 나눠 쓰는 지금 설계로 충분한가요?**

## 4. 벤더 조건 — 세 칸으로

### 확인된 것

| | |
|---|---|
| **보존 통제** | **API 기본 30일 보관**(암호화·감사용) 후 자동 삭제. **API 데이터로 학습하지 않는다.** **ZDR 있음** — 켜면 입력·출력이 디스크에 남지 않는다 |
| **대상 연령** | **소비자 약관**은 13세 이상, 13~18세는 보호자 허락. ⚠️ **API에 대해서는 확인한 범위에서 확인되지 않았다** |
| **보호자 동의** | 엔터프라이즈 약관에 ZDR 사용 시 *"Customer만이 개인정보를 보유·접근하며, 모든 개인정보가 ZDR 활성 API로만 처리되도록 할 책임은 Customer에게 있다"* |

### 조건부 함의

**OpenAI와 구조가 같다** — ZDR이 있고, 아동 데이터를 쓰려면 그걸 먼저 켠다. **TypeSafe와는 반대다**(거긴 ZDR이 문서에 없고 정책이 18세 미만을 배제한다).

**그리고 ZDR을 켜면 책임이 우리에게 온다.** *"모든 개인정보가 ZDR 활성 API로만 처리되도록 할 책임은 Customer에게"* — 즉 **한 군데라도 ZDR 안 켠 엔드포인트로 새면 우리 책임**이다. 판정·낭독·받아쓰기가 다 같은 조직이면 **전부 확인해야 한다.**

### 확인되지 않은 것

- **개인정보 정책 원문** — 403으로 막혔다. 다시 시도하거나 다른 경로로 봐야 한다
- **API 이용자의 최종 사용자가 13세 미만일 때**의 조항. 소비자 약관은 읽었지만 **API/엔터프라이즈 쪽은 안 읽었다**
- ZDR을 어떻게 켜는가 — 콘솔 설정인지 영업 문의인지

### 같이 생각해 볼 질문

- 벤더가 셋이 되면(OpenAI 판정·낭독 / xAI 받아쓰기 / 자체 그림) **ZDR을 세 군데 다 확인해야** 하나요?
- 한 벤더로 몰면 관리가 쉬운데, **OpenAI에도 받아쓰기가 있습니다**(`gpt-4o-mini-transcribe`). 핵심 낱말 편향이 거기도 있나요?

## 5. 그래서 무엇을 하나

### 정했다

- **후보 목록에 올린다.** 자체 `faster-whisper` · `gpt-4o-mini-transcribe` · **`grok-voice-transcribe-2.0`** 셋
- **편향을 축에 넣는다.** 자체 whisper에도 `initial_prompt`로 프리셋을 밀어 넣고 **같은 조건에서** 비교한다
- **아이 음성 30발화가 와야 정한다**는 것은 그대로다. 후보가 늘어도 이 제약은 안 변한다

### 안 정했다

- **A(자체)냐 B(외부)냐.** 이건 정확도가 아니라 **규칙 6을 바꿀 것인가**의 문제다 — 팀 결정이다
- 배치냐 스트리밍이냐
- 아이가 실명을 얼마나 말하는지 (B의 무게를 정하는 값)

### 다음 — 의존성 순

1. **프리셋 낱말을 세고 100개 안에 드는지 본다** — 안 들면 편향 기능을 다 못 쓴다
2. **자체 whisper에 `initial_prompt`로 프리셋을 넣고 다시 잰다** — 65%가 얼마나 오르는지. **이것만으로 합격선을 넘으면 밖으로 안 보내도 된다**
3. 아이 음성 30발화가 오면 **세 후보를 같은 음성·같은 편향으로** 돌린다
4. ZDR 확인 — 멘토 조사 2번의 콘솔 항목과 같이

**2번이 제일 값싸고 제일 많이 바꾼다.** 코드 한 줄이고, 통과하면 3절의 A/B 논쟁 자체가 사라진다.
