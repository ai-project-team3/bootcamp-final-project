## 0. 이 문서를 읽는 법

기획안은 제품 문서라 데이터 모델·API·폴더 구조가 없습니다.
그 공백 17개를 찾아 P0~P3으로 나누고, 담당자가 각각 결정서를 썼습니다.

| 티어 | 성격 | 결정 주체 | 개수 |
|---|---|---|--:|
| **P0** 계약 | 안 정하면 아무도 코드를 못 씀. 서로 물려 있어 분해 불가 | 조장 + 진웅 | 4 |
| **P1** 외부 검증 | 결과가 기획을 뒤집을 수 있음 | 담당자 조사 → 전원 판단 | 4 |
| **P2** 동작 규칙 | 내 모듈이 어떻게 동작하는지 | 담당자 결정 | 4 |
| **P3** 운영·발표 | 늦어도 되지만 지금 정하면 설계가 편함 | 담당자 결정 | 5 |

전체 근거는 `gaps/01~17`에 있습니다. 여기는 **결정과 한 줄 근거**만 모았습니다.

## 1. 역할 5분할

**분할 기준은 "내가 만든 기능"이 아니라 "내가 책임진 지표"입니다.**

최종발표는 10분 발표 + **Q&A 20~30분**입니다. 현직자가 묻는 건 *"뭘 만드셨어요?"* 가 아니라
*"얼마나 정확해요, 어떻게 측정했어요, 뭘 해서 올렸어요?"* 입니다. 세 번째에 답하려면
각자 자기 숫자가 있어야 합니다.

| 역할 | 트랙 | 소유 | 지표 |
|---|---|---|---|
| **1** 음성·실시간 | A | 오디오 캡처 · STT · 화자 분리 · WebSocket · 세션/방 · 백채널 | WER · p95 지연 · 드롭률 |
| **2** 항목 매칭 | A | 표현사전 + 임베딩 하이브리드 · 기타 처리 · 임계값 | 매칭 F1 · 기타 오분류율 |
| **3** 상태 추적 | A | 상태 전이 · 재발 판정 · 공통 평가 러너 | 상태 정확도 · **재발 재현율** ★ |
| **4** 생성 | B | 카드 규칙 + LLM 문장 · 차수별 리포트 | 카드 채택률 · 근거 인용률 |
| **5** 템플릿·누적 (조장) | B | 항목풀 저작 · 이월 규칙 · 딜 연결 | 이월 정확도 · 템플릿 커버리지 |

**각자 백엔드와 자기 화면을 함께 소유합니다.** "프론트 담당"이라는 자리를 두지 않은 이유는
AI 부트캠프에서 가장 팔기 어려운 자리이기 때문입니다.

**병렬성은 fixture가 만듭니다.** W0에 라벨된 역할극 JSON을 만들면 역할 2·3·4가
전사 없이 첫날부터 채점하며 개발할 수 있고, 역할 1은 "이 JSON을 실시간으로 뱉기"가 목표가 됩니다.
**아무도 서로를 기다리지 않습니다.**

## 2. P0 — 계약 넷

### `#1` 화자 분리 방식

**결정**: `SpeakerSource` 인터페이스로 추상화. **MVP는 `DualChannelSource`(화상·노트북 통화)만.**
대면·스피커폰은 `EnrolledVoiceSource`로 W4 조건부.

**근거**: 화상은 내 마이크와 탭 오디오가 물리적으로 다른 채널이라 화자 정확도가 100%이고
`confidence`가 항상 1.0입니다. 대면을 넣으면 **ML 난제가 두 개**가 되고,
재발 재현율이 낮게 나왔을 때 **모델 탓인지 화자 분리 탓인지 구분할 수 없습니다.**

**등록 단계를 만들지 않습니다.** 영업사원은 앱 최초 1회 등록하고, 상대는 미팅 첫 인사 구간에서
자동 수집합니다. 상담 자리에 없던 절차를 끼워 넣으면 상대가 방어적으로 변하고,
그 손해가 정확도로 얻는 이득보다 큽니다.

**고지는 허락을 구하지 않습니다.** 부담의 원인은 "녹음"이라는 단어가 아니라 **"괜찮으실까요?"라는
질문 형태**입니다. 질문은 거절 선택지를 만들고, 거절당하면 제품이 못 돕니다.
🟢 *"이야기 정리하려고 녹음 켜두겠습니다."* / 🔴 *"메모 도구를 좀 쓰겠습니다"* (숨김) — 후자는 안 씁니다.

### `#2` 항목 풀 스키마

**결정**: 전역 카탈로그 + 템플릿은 참조. `Item{id, label, aliases(5), keywords, slots}`,
`Slot{key, label, cues(3), blockers(3)}`. YAML로 쓰고 Pydantic으로 검증.

**근거 셋**

- **예문 리스트** — 정규식은 조장이 유지보수할 수 없고, 키워드로는 "위에 물어봐야"처럼
  단어가 안 겹치는 표현을 못 잡습니다
- **슬롯** — §4-2의 "금액과 승인 절차가 둘 다 나와야"를 일반화한 것. **슬롯이 🟡을 자동으로
  정의**하고, 정의가 없으면 채점할 수 없습니다
- **전역 카탈로그** — 템플릿 로컬 ID면 차수 간 이월에서 ID가 안 맞습니다. **해자가 깨집니다**

**예문은 씨앗 5개만 씁니다.** 항목 40개 × 10개면 400문장이라 W1에 못 씁니다.
부족한 밀도는 fixture 라벨링에서 나오는 실제 발화(`harvested`)로 메웁니다 —
**어차피 해야 하는 작업이 표현 사전을 두껍게 만듭니다.**

**검증 규칙이 조기 경보를 겸합니다** — 슬롯 5개 초과 = 항목을 쪼개라, 2층 12개 초과 = 합쳐라.

### `#3` 상태 전이표

**결정**: 4상태 + **상태변화 리스트 단일 관리**. 재발은 `RANK` 역전으로 파생.

```python
State = Literal["unseen", "raised", "partial", "resolved"]
RANK  = {"unseen": 0, "raised": 1, "partial": 2, "resolved": 3}
재발 = RANK[to_st] < RANK[from_st]
```

**근거**: 재발을 5번째 상태로 두면 재발 후 일부 풀렸을 때 **이력이 사라지고** 두 번 재발한 것을
구분할 수 없습니다. 사건으로 두면 몇 번이든 쌓이고, **§6-2가 요구한 "재발을 따로 측정"이
사건 검출 문제가 되어 재현율이 그대로 나옵니다.**

현재 상태를 따로 저장하지 않고 리스트에서 파생하면 **화면 ② 타임라인이 자료구조 그 자체**가 됩니다.

**자동 확정합니다.** §5-1이 금지한 건 "완료" 처리로 **오탐이 안심시키는 방향**이기 때문입니다.
재발 오탐은 *"이미 푼 걸 다시 보세요"* 라 위험을 만들지 않습니다. 탭으로 되돌리고 그게 로그로 남습니다.

**이월은 이전 차수 색을 그대로 가져옵니다.** 신호등의 정의가 *"상대가 지금 걸려 있는 것"* 인데,
1차에서 막혔고 그 사이 아무 일도 없었으면 2차 시작 시점에도 **여전히 막혀 있습니다.**
⚪는 사실과 다릅니다. `trigger="carryover"`로 기록하고 지표에서 뺍니다.

**2층은 신호등이 아닙니다.** 상태 2개, 단조 증가, 재발 없음, 인터랙션도 다릅니다.
화면에서 열을 분리했습니다.

### `#4` 미팅 ↔ 고객 연결키

**결정**: 연결 단위는 **딜(건)**. 사용자 수동 선택. 사후 연결 허용. `unlink` 필수.

**근거**: 영업의 실제 단위는 회사도 사람도 아니고 "이 건"입니다. Salesforce·HubSpot이
전부 Deal 단위인 이유이고, §2-2의 *"1차 발견 / 2차 변화 / 3차+ 패턴"* 이 딜의 수명주기입니다.
회사 단위면 담당자 교체 시 이월이 어색해지고, 사람 단위면 B2B에서 이력이 쪼개집니다.

**자동 매칭을 쓰지 않습니다.** 이 결정의 유일한 치명적 실패 모드가 **잘못 잇는 것**입니다.
*"지난번에 예산 승인이 재발했습니다"* 를 처음 만나는 고객에게 띄우면 제품 신뢰가 끝납니다.

`Deal.voice_ref` 한 줄이 `#1`과 물립니다 — 대면 모드에서 1차에 등록한 상대 목소리를 저장해두면
**2차부터 등록 구간이 사라집니다.**

## 3. P1 — 외부 검증 넷

### `#5` 되돌아감이 실제로 자주 일어나나 ⚠️ **미완**

**결정**: 재발은 실재하고 흔한 현상으로 간주하고 설계한다.

**근거** 🔍: Gong Labs가 B2B 영업 통화 **20,858건**을 감정 점수로 분석한 결과, 놓친 거래가
성사된 거래보다 감정 점수가 **12.8% 더 높게** 나왔습니다 — 긍정 일변도보다 오르내리는 쪽이
오히려 성사된다는 뜻이라, 반응이 단조롭지 않다는 간접 증거입니다.
"Happy Ears Syndrome"이 업계 용어로 자리잡은 것도 같은 방향입니다.

⚠️ **"한 미팅에 몇 번"은 끝내 못 찾았습니다.** 여러 벤더 리포트와 학술자료를 뒤졌지만
"call당 평균 sentiment shift 횟수" 같은 지표는 **애초에 공개된 적이 없습니다** — 각 벤더가
자사 고객 데이터로만 내부 분석하는 영역입니다.

**남은 일**: 현업 영업사원 1~2명 인터뷰. 이건 온라인 리서치로 대체 불가입니다.

### `#6` 미팅 중 화면을 볼 수 있나

**결정**: 영업사원 **본인만 보는 화면(2nd 디바이스)이 항상 존재한다**고 가정하고 설계한다.

**근거** 🔍: **초안의 "대면 = 화면 없음"은 재조사로 폐기됐습니다.** 국내 보험업계는 이미
설계사에게 태블릿을 지급해 고객관리·가입설계·전자서명을 현장에서 처리합니다.
다만 그 태블릿은 **고객에게 보여주는 공용 화면**이라 코칭 문구를 띄울 수 없습니다.

**국내 생명보험 가입의 93%가 설계사·GA(대면·전화) 채널입니다** 🔍.

> ⚠️ **조장 결정으로 MVP는 화상 유지입니다.** `#6`의 "전 시나리오 UI"는 W4로 미룹니다.
> 시장 판단이 아니라 **난제를 하나로 유지하기 위한 선택**이고, 발표에서 이 구분을 말해야 합니다.
> 이건 검증된 사실이 아니라 **팀이 채택한 설계 가정**이라는 점도 기록해 둡니다.

### `#7` Caret 종료의 진짜 이유

**결정**: 종료 사유는 확인 불가로 인정하고, §7-3에서 근거로 쓴 문장을 **"추정"으로 표시**한다.
**Aside 캐럿 차별점 슬라이드를 따로 만든다.**

**근거** 🔍: caret.so 공식 changelog는 **404**, 티로 마이그레이션 글에도 "종료됨"만 있고
이유는 없습니다. 창업자 인터뷰·언론 보도도 없습니다. **더 찾으면 나올 자료가 아니라 비공개 정보**입니다.

🔴 **중대 발견**: **"캐럿"이라는 이름의 전혀 다른 회사가 있습니다.**
Aside(대표 김효준)의 캐럿은 **"기술 영업팀을 위한 실시간 AI 코파일럿"** 으로, 고객 질문이
나오면 내부 문서·과거 성공사례 기반으로 실시간 답변을 추천합니다.
**우리 컨셉과 거의 동일**하고, 종료된 게 아니라 **YC F25 선정 + 프리시드 15억으로 운영 중**입니다.

발표에서 **먼저 꺼내야** 합니다. 안 꺼내면 Q&A에서 나옵니다.

### `#8` 항목이 30~50개로 닫히나

**결정**: 보험 상담 한 종을 끝까지 써서 **39개**로 닫힘을 확인.

| 카테고리 | 개수 |
|---|--:|
| A 오프닝/라포 | 3 |
| B 니즈분석-기본정보 | 7 |
| C 니즈분석-리스크 | 6 |
| D 상품설명 | 8 |
| E 반론처리 | 5 |
| F 청약/클로징 | 6 |
| G 컴플라이언스 (법정 필수) | 4 |

G는 임의로 만든 게 아니라 **"3대 기본지키기"**(청약서 부본 전달 · 약관 전달 및 중요내용 설명 ·
계약자 자필서명) 🔍가 근거입니다. 이행하지 않으면 3개월 이내 청약철회·환급이 가능합니다.

> 🔴 **`#2`와 합치면 문제가 드러납니다.** 이 39개는 **1층 반대사유 풀이 아닙니다.**
> A·B·C·D·F·G는 전부 "내가 해야 할 일"이고 **반대사유는 E 5개뿐**입니다.
> 이 분류대로면 2층이 34개가 되어 12개 상한을 크게 넘습니다.
>
> **W1 차단 항목** — E를 세분화해 1층 30개를 만들고, 2층은 G + D 중 금소법 해당분에서
> 12개 이하로 추립니다. A·B·C·F는 1차에서 제외합니다.

## 4. P2 — 동작 규칙 넷

### `#9` 실시간 지연 예산

**결정**: `utterance_end` → 신호등 반영 **p95 3초**, 카드 갱신 **p95 5초**. **분리 측정.**

**근거**: 핵심은 상태 변화가 실시간으로 보이는 것이고 카드는 그 뒤에 따라오는 보조입니다.
카드에는 LLM 생성 시간이 포함되어 변동폭이 크므로 같은 SLA로 묶으면 난도만 올라갑니다.
평균은 느린 구간을 가리므로 **p95**를 공식 지표로 씁니다.

타임스탬프 여섯 지점 — `utterance_end` `stt_final` `match_done` `state_updated`
`state_rendered` `card_rendered`. **W1의 목표는 3초 달성이 아니라 어디서 시간이 소비되는지
보이는 상태를 만드는 것입니다.**

### `#10` 콜드 스타트 대응

**결정**: 1차는 **"이번 미팅 기본 체크" 5개**를 같은 항목 풀에서 골라 보여주고,
2차부터 실제 이월을 최우선으로 표시한다.

**근거**: 1차에는 과거 상태가 없는데 "지난번 미해결"을 임의로 만들면
**상태 지속성의 신뢰를 훼손합니다.** 반대로 비우면 첫 사용 시 제품 가치가 약해 보이고
발표에서도 "첫 미팅에서는 뭘 해주나"가 남습니다.

**기본 5개는 과거 상태처럼 표시하지 않고 별도 영역**으로 보여줍니다.

### `#11` 필수 항목 미완료 처리

**결정**: `종료 전 경고 → 리포트 상단 고정 → 다음 차수 자동 이월` 3단계.
**종료 자체를 막지 않는다.**

**근거**: 실제 미팅은 고객 사정으로 갑자기 끝납니다. 시스템이 하드 블록하면 사용성이 떨어집니다.

🔒 **이 기능은 법적 준수를 보장하지 않습니다.** 발표에서도 "미완료 항목 추적 및 경고"까지만
말합니다. 시스템이 법적 판정을 내리는 게 아니라 **사용자가 놓친 항목을 추적하고 다시 노출하는
보조 기능**입니다.

### `#12` 네트워크 끊김 처리

**결정**: **서버가 authoritative source.** 상태 변화 때마다 즉시 스냅샷.
같은 `session_id`로 재접속하면 최신 스냅샷을 다시 받는다.

**근거**: 핵심 데이터는 원문 오디오가 아니라 **현재 상태와 그 근거**이므로 상태 변화 시점을
기준으로 저장하면 가장 중요한 정보 손실을 줄입니다. 주기 저장은 저장 직후 상태가 바뀌고
끊기면 최신을 잃습니다.

**끊김이 있었다는 사실을 UI에 표시합니다** — 누락 구간이 없는 것처럼 보이지 않게.
끊긴 동안의 오디오 완전 복구는 MVP 범위 밖입니다.

## 5. P3 — 운영·발표 다섯

### `#13` 녹음 고지 흐름 🔍 **법률 조사 포함**

**결정**: `☐ 미팅 참여자에게 녹음 사실을 안내했습니다` 체크박스. **강제하지 않는다.**
**백채널에 음성을 전송하지 않는다.**

**근거 1 — 당사자 녹음은 처벌 대상이 아닙니다** 🔍

통신비밀보호법 제3조·제14조·제16조가 모두 **"타인간의 대화"** 를 대상으로 합니다.
본인이 참여한 대화를 스스로 녹음하는 경우는 해당하지 않아 형사처벌 대상이 아니고
사전 고지 의무도 없습니다. 2022년 개정안이 발의됐으나 철회됐습니다.

**강제할 법적 근거가 없는데 강제하면 마찰만 생깁니다.**

**근거 2 — 🔴 그런데 백채널이 이 안전지대를 깹니다** 🔍

**대법원 2024. 2. 29. 선고 2023도8603** — 거실 홈캠에 녹음된 대화를 나중에 재생해 들은 사안에서
**"대화가 종료된 뒤 재생해 듣는 것은 청취가 아니다"** 로 무죄. 그 과정에서
**'청취'를 "대화가 이루어지는 도중에 실시간으로 듣는 행위"로 확정**했습니다.

**원격 동석자에게 음성을 실시간 전송하면 정확히 이 정의에 들어갑니다.**

**근거 3 — 통제 지점을 "누가 접속하는가"가 아니라 "무엇을 보내는가"에 둡니다**

방 코드는 전화로 불러줄 수 있어 동석 여부를 기술적으로 검증하지 못합니다.
**실효적인 통제는 음성을 아예 보내지 않는 것입니다.** §2-4의 백채널은 원래 음성이 필요 없으므로
제약이 기능을 깎지 않습니다.

> ⚠️ **법률 자문이 아닙니다.** 조문과 판례는 확인했으나 제품 상황에 적용한 해석은 담당자 판단입니다.
> 최종 서비스에서는 변호사 검토가 필요합니다.

### `#14` 백채널 접속 방법

**결정**: **6자리 방 코드** → 짧은 수명의 `joinToken` → 접속. 미팅 종료와 동시에 폐기.

**근거**: 데모/PoC에 계정·팀 개념이 없고, 발표에서 2인 접속을 보여줘야 하는데 로그인이 들어가면
화면이 두 번 넘어갑니다. 6자리 코드는 **말로도 전달됩니다.**

🔴 **방 코드는 보안 장치가 아닙니다.** 실효적 통제는 `#13`의 "음성 미전송"입니다.

### `#15` 평가 데이터 규모

**결정**: 재발 **40건** 목표 → 역할극 **25세션(300분)**.

```
목표 재발          40건
세션당 심는 수      2건    ← PoC 실측 상한
                 ─────
양성 세션          20세션
+ 음성 대조군       5세션   ← 재발 0건. 오탐 측정용
                 ─────
총                25세션 × 12분 = 300분  → 5명이 1인당 8시간
```

**세션당 2건이 자연스러움의 상한입니다** 🔍 — PoC 평가셋에 직접 써보니
3건 이상이면 "고객이 계속 말 바꾸는 사람"이 됩니다.

**라벨링**: 전량 1명 + **20%(5세션)를 2명이 독립 라벨링**해 Cohen's κ 계산. 평가 단위는 **발화**.

| 지표 | PoC 목표 |
|---|---:|
| 재발 재현율 | ≥ 0.80 |
| 정확도 · F1 | 함께 측정 |
| Cohen's κ | ≥ 0.61 |

🔴 **"심어서 측정했다"를 발표에서 먼저 말합니다.** 자연 발생만 기다리면 50세션 이상이 필요해
6주에 불가능합니다. 숨기면 Q&A에서 깨지고, 먼저 말하면 방법론을 안다는 신호가 됩니다.
40건에서 0.80을 관찰해도 표본이 작아 불확실성이 크므로 **PoC 검증 결과로 제한해 보고**합니다.

### `#16` 데모 시나리오

**결정**: 발표 기본은 **전사 fixture 재생**. 라이브 마이크는 **보조**.

**근거**: 라이브는 마이크 권한·소음·에코·STT 지연·네트워크가 결과에 영향을 줍니다.
**하나만 터져도 10분 발표에서 회복할 시간이 없습니다.**

```
오디오 fixture   재생 → STT 호출 → 결과 대기 → 파이프라인
                       ↑ 발표장 네트워크·API 장애가 여기 다 걸림

전사 fixture     파일 읽기 → 파이프라인
                 ↑ 네트워크 의존 0
```

STT 단계의 외부 의존성을 제거하면서도 **분석 이후 파이프라인은 그대로 실행**됩니다.
녹화 영상과 달리 "실제로 도는 것"을 보여줄 수 있습니다.

🔴 **fixture도 안전하지 않습니다** 🔍 — PoC에서 탭이 백그라운드가 되자
`setInterval`이 스로틀되어 **9초에 8발화만** 진행됐습니다(정상이면 30발화 이상).
**그래서 호출 횟수가 아니라 timestamp 기반으로 재생 위치를 계산합니다.**

발표 10분 안에 **재발이 최소 1회** 나오도록 구성하고, 핵심 이벤트를 **2~4분 구간**에 배치합니다.

### `#17` 배포 구성

**결정**: 프론트 **Cloudflare Pages** / 백엔드 **Railway Hobby($5/월)** / DB **Railway MySQL** /
Durable Objects **미채택** / 코드 프리즈 **9/22 · 10/17**.

**근거 1 — 무료 티어를 쓰지 않습니다**

```
발표 순서를 기다린다 → 20~30분 무요청 → 무료 호스팅 sleep
→ 데모 시작 버튼 → 재기동 대기 → 실시간 데모 지연
```

Render 무료는 15분 무요청 시 sleep하고 재기동에 약 1분. **WebSocket이 장시간 연결을 유지하는
구조라 sleep이 치명적입니다.** Railway에서도 Serverless를 쓰지 않는 상시 실행으로 운영합니다.

**근거 2 — Cloudflare Workers를 백엔드로 쓰지 않습니다**

Python Workers가 FastAPI를 지원하지만 **직접 소켓 접근이 없어 SQLAlchemy가 MySQL에 붙지 못합니다.**
데이터 계층을 통째로 바꿔야 하고 6주 안에 감당할 비용이 아닙니다.
MySQL로 바꿔도 동일합니다.
